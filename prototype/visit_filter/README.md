# ต้นแบบชั้นกรอง visit

รวม `enter`/`exit` ดิบที่กระพริบทั้งคืนให้เหลือ **การมาเยือนจริง** — เขียนเป็น
**reducer บริสุทธิ์** ไม่ผูกกับ `beacon_kit`

> **สถานะ: ตัดสินแล้วว่าตรรกะนี้จะทำงานฝั่ง native ทั้ง Kotlin และ Swift**
> (เพราะต้องยิงแจ้งเตือนตอนแอปปิดอยู่)
>
> **เวอร์ชัน Dart นี้เป็นข้อกำหนดอ้างอิงและชุดเทสต์ต้นแบบ ไม่ใช่โค้ดที่จะรันบน
> เครื่องผู้ใช้** — อยู่ใต้ `prototype/` ไม่ใช่ `packages/` โดยตั้งใจ ไม่มีแพ็กเกจ
> ไหนใน repo พึ่งพามัน และไม่ถูกรวมเข้า build ของ SDK ที่ไหนเลย
>
> 📄 **[`PORTING.md`](PORTING.md)** — จุดที่พอร์ตไปสองภาษานั้นไม่ตรงกัน และกลไก
> `vectors.json` ที่กันไม่ให้สามที่เพี้ยนจากกัน · **อ่านก่อนเขียน port**
> 📄 **[`SENSING.md`](SENSING.md)** — observation ชนิด "ตอบไม่ได้" · ฝั่ง native จะ
> ตรวจได้อย่างไร และกรณีไหนที่รู้ไม่ได้เลย

```bash
cd prototype/visit_filter
dart pub get
dart test                          # 73 เทสต์ · รวม log จริงสองคืน + conformance vector
dart run bin/cooldown_sweep.dart   # หา cooldown ต่ำสุดที่ยังผ่านเกณฑ์รับ
dart run bin/generate_vectors.dart # สร้าง spec/visit_filter/vectors.json ใหม่ (ต้อง commit)
```

## สัญญาของ reducer

```dart
VisitReduction reduce(VisitFilterState state, VisitObservation observation)
//                   (state,                 observation)  ->  (newState, emittedEvents)
```

**ห้ามทั้งหมดนี้ และเป็นข้อบังคับ ไม่ใช่สไตล์:**

| ห้าม | เพราะ |
|---|---|
| `Timer` | ฝั่ง Android กระบวนการที่ระบบปลุกมาเพื่อ `onReceive` มีอายุหลักสิบมิลลิวินาที · `Timer` ที่ตั้งไว้ตายไปกับ process **โดยไม่มีอะไรฟ้อง** |
| `Stream` ที่มีสถานะภายใน | สถานะในหน่วยความจำหายไปพร้อม process เดียวกัน — ผ่านเทสต์ในเครื่อง พังบนอุปกรณ์จริง |
| อ่านนาฬิกาเอง | เวลาต้องมาจาก observation เสมอ เพื่อให้เล่นซ้ำจากไฟล์ log ได้ผลเดียวกันทุกครั้ง |

`VisitFilterState` เป็น **ข้อมูลล้วน ไม่มีพฤติกรรม** ตั้งใจให้ผู้เรียกเก็บลง
`SharedPreferences` / `UserDefaults` ระหว่าง event

### observation

| ชนิด | ความหมาย |
|---|---|
| `RegionSeen` | แพลตฟอร์มยืนยันว่า **อยู่** ณ เวลานั้น (iOS `didEnterRegion` · Android ผลสแกนจาก `PendingIntent`) |
| `RegionNotSeen` | แพลตฟอร์มยืนยันว่า **ไม่อยู่แล้ว** (iOS `didExitRegion` · Android นาฬิกาปลุก exit ของเราเอง) |
| `TimeAdvanced` | เวลาเดินไปถึงแล้ว แต่ไม่มีข้อมูลใหม่ว่าอยู่หรือไม่ — **ป้อนทุกครั้งที่ถูกปลุก** |
| `SensingLost` | **เราตาบอด ตอบไม่ได้ว่าอยู่หรือไม่** (Bluetooth ปิด · ไม่มีสิทธิ์ · ฯลฯ) — มีผลกับทุก region · **นาฬิกา cooldown หยุด** |
| `SensingRestored` | มองเห็นได้อีกครั้ง — ช่วงที่ตาบอดถูก**หักออก**จากความเงียบ |
| `ObservationsEnded` | ไม่มีอะไรตามมาอีก — ปิดการมาเยือนที่ยังค้างที่ **ขอบข้อมูล** |

### event

`VisitStarted(at, evidence)` · `VisitEnded(startedAt, endedAt, reason)`

`evidence` แยก **`arrivalObserved`** (เห็นการเปลี่ยนจากไม่อยู่เป็นอยู่จริง) ออกจาก
**`alreadyInsideAtFirstObservation`** (ข้อมูลเริ่มตอนอยู่ในโซนอยู่แล้ว — `at` เป็น
**ขอบบน**ของเวลาที่มาถึง ไม่ใช่เวลาที่มาถึง)

`reason` แยก **`cooldownElapsed`** (จบสมบูรณ์) ออกจาก **`observationsEnded`**
(ข้อมูลหมดขณะยังเปิดค้าง — ยังไม่รู้ว่าจบจริงเมื่อไร ห้ามรายงานเป็นการมาเยือนที่จบแล้ว)
และจาก **`sensingLostBeyondCeiling`** (ตาบอดนานเกินเพดาน — **ไม่ได้แปลว่าผู้ใช้ออกไป**
แปลว่าเราขาดข้อมูลนานเกินกว่าจะอ้างความต่อเนื่องได้ · `endedAt` อาจเก่ากว่าเวลาที่
ผู้ใช้ออกไปจริงมาก **ห้ามใช้คำนวณระยะเวลาที่อยู่ในสาขา**)

## กฎที่ทำให้มันไม่พัง

### 1. state แยกต่อ region

`Map<String, RegionState>` ไม่ใช่ตัวแปรรวมตัวเดียว · ตอนนี้มี region เดียวจึงยังไม่
เห็นปัญหา แต่ทันทีที่มี region ที่สอง เหตุการณ์ "ออกจากสาขา A แล้วเข้าสาขา B" จะถูก
กลืนหายทั้งคู่

การตัดสินหลาย region พร้อมกัน (`TimeAdvanced` / `ObservationsEnded`) **ไล่ตามลำดับ
identifier เสมอ** เพื่อให้ลำดับ event ไม่ขึ้นกับลำดับที่ key ถูกใส่เข้า map — สำคัญ
กับการพอร์ตไป Kotlin/Swift ที่ `Map` ไม่รับประกันลำดับเหมือนกัน

### 2. ครบ cooldown แล้ว **ต้องดูสถานะปัจจุบันก่อน**

```
ครบ cooldown
├── ยังเห็น beacon อยู่ → ไม่ยิงอะไร · การมาเยือนครั้งเดิม
└── ไม่เห็นแล้ว        → ปิดการมาเยือน · ครั้งหน้าที่เจอค่อยยิง VisitStarted
```

ถ้าเขียนเป็น "ครบเวลาแล้วยิงเลย" จะได้ `VisitStarted` ปลอมทุก cooldown
**ตลอดเวลาที่ลูกค้าอยู่ในร้าน**

สาขา "ยังเห็นอยู่" **ถูกเรียกจริงกับข้อมูลจริง ไม่ใช่กันไว้เฉย ๆ**: ไฟล์ iOS คืน
30 ส.ค. มีช่วงที่อยู่ในโซนต่อเนื่อง **3 ชั่วโมง 10 นาที** โดยไม่มี event ใดเลย
ระหว่างนั้นมีบรรทัด `launch` ที่ถูกป้อนเข้ามาเป็น `TimeAdvanced` — ถ้าไม่มีการ์ดนี้
การมาเยือนจะถูกปิดกลางคัน แล้ว `enter` ถัดไปกลายเป็น `VisitStarted` ปลอมทันที

### 3. ความเงียบนับจาก "ประกาศว่าไม่เห็น" ไม่ใช่ "เห็นครั้งสุดท้าย"

ระหว่างที่ยังอยู่ในโซน แพลตฟอร์ม**ไม่ส่งอะไรมาเลย** — `lastPresentAt` จึงเก่ากว่า
cooldown ได้เป็นชั่วโมงทั้งที่ผู้ใช้ยังนั่งอยู่ที่เดิม การนับความเงียบจาก
`RegionNotSeen.at` เป็นสิ่งเดียวที่ให้ผลตรงกับกติกา "รวมคู่ที่ห่างกัน < N นาที"
ใน `docs/test-data/GROUND_TRUTH.md`

`exit` ซ้ำติดกันไม่เลื่อนจุดเริ่มความเงียบ มิฉะนั้น cooldown จะไม่มีวันครบถ้า
แพลตฟอร์มยิง `exit` ถี่กว่า cooldown

### 4. `VisitEnded.endedAt` คือหลักฐานสุดท้ายที่เห็น ไม่ใช่เวลาที่รู้ตัว

ถ้ารายงานเวลาที่รู้ตัว ทุกการมาเยือนจะยาวเกินจริง**เท่ากับ cooldown พอดี**

## ผลกับ log จริงสองคืน

ทั้งสองไฟล์ผ่านด้วย **พารามิเตอร์ชุดเดียวกัน** (`cooldown = 5 นาที` — ค่าที่ ADR-11
เสนอไว้) ไม่ต้องแยกค่าตามแพลตฟอร์ม

| | iOS 30 ส.ค. | Android 1 ก.ย. |
|---|---|---|
| `enter`/`exit` ดิบ | 86 / 86 | 63 / 62 |
| **`VisitStarted`** | **1** ✅ | **1** ✅ |
| เริ่ม (local +07:00) | `2026-08-30T18:34:47.313+07:00` | `2026-09-01T15:50:11.073+07:00` |
| จบ (ปิดที่ขอบข้อมูล) | `2026-08-31T08:41:07.768+07:00` | `2026-09-02T08:48:34.516+07:00` |
| ระยะเวลา | 14 ชม 6 น 20 วิ | 16 ชม 58 น 23 วิ |
| `evidence` | `arrivalObserved` | `alreadyInsideAtFirstObservation` |
| `reason` | `observationsEnded` | `observationsEnded` |
| observation ที่รับไม่ได้ | 0 | 0 |

ตรงกับตารางเกณฑ์รับใน `GROUND_TRUTH.md` ทุกช่อง

**`evidence` ต่างกันเพราะไฟล์ต่างกันจริง ไม่ใช่เพราะแพลตฟอร์มต่างกัน** — ไฟล์ iOS
มีบรรทัด `exit` นำหน้า `enter` แรก reducer จึงเห็นการมาถึงจริง ส่วนไฟล์ Android
เริ่มด้วย `enter` เลย จึงตอบได้แค่ว่า "พบว่าอยู่ในโซนตั้งแต่ observation แรก"

## cooldown ต่ำสุดที่ยังผ่าน — **ห้ามใช้เป็น default**

`dart run bin/cooldown_sweep.dart` (bisect ความละเอียด 1 มิลลิวินาที):

| | ต่ำสุดที่ผ่าน | ช่วงเงียบยาวสุดในไฟล์ | ระยะห่าง |
|---|---|---|---|
| iOS 30 ส.ค. | **209 191 ms** (3 น 29.191 วิ) | 209 190 ms (3 น 29.190 วิ) | **1 ms** |
| Android 1 ก.ย. | **183 744 ms** (3 น 3.744 วิ) | 183 743 ms (3 น 3.743 วิ) | **1 ms** |
| **ใช้ได้ทั้งสองไฟล์** | **209 191 ms** | — | **1 ms** จากขอบของ iOS |

⚠️ **ค่านี้อยู่ห่างจากขอบ 1 มิลลิวินาที** — มันคือ "ค่าที่พอดีกับข้อมูลสองชุดนี้เป๊ะ"
ไม่ใช่ค่าที่ปลอดภัย คืนถัดไปที่เงียบนานกว่าเดิมแค่เสี้ยววินาทีจะได้ visit ปลอมทันที
และช่วงเงียบยาวเป็นอันดับสองของ iOS อยู่ที่ 201 070 ms ห่างจากอันดับหนึ่งแค่ 8.1
วินาที — หางของการแจกแจงยังไม่นิ่งพอจะสรุปเพดาน

ระยะห่างจากขอบเมื่อเลือกค่าอื่น:

| cooldown | visit (iOS / Android) | เผื่อเหนือช่วงเงียบที่แย่ที่สุด |
|---|---|---|
| 3 น 29.191 วิ | 1 / 1 | **1 ms** (0.0%) |
| 3 น 30 วิ | 1 / 1 | 0.810 วิ (0.4%) |
| 4 นาที | 1 / 1 | 30.810 วิ (14.7%) |
| **5 นาที** | 1 / 1 | **1 น 30.810 วิ (43.4%)** |
| 10 นาที | 1 / 1 | 6 น 30.810 วิ (186.8%) |

ค่า 5 นาทีของ ADR-11 ให้เผื่อ **43.4%** เหนือช่วงที่แย่ที่สุด — ตรงกับตัวเลขที่
ADR-11 หัวข้อ 5 คำนวณไว้ (~43%) โดยคำนวณคนละทาง

**แพ็กเกจนี้จงใจไม่มีค่า default ให้ `cooldown`** — ผู้เรียกต้องเลือกเอง

## สิ่งที่ reducer นี้ **ยังไม่ทำ**

- **เกณฑ์ "ต้องอยู่อย่างน้อยกี่นาที" (ADR-11 ข้อ ข.)** — `VisitStarted` ถูกยิงทันที
  ที่เห็นครั้งแรก การกรองด้วยระยะเวลาต้อง**เลื่อนการยิงออกไป**จนกว่าจะรู้ว่าอยู่นาน
  พอ ซึ่งใน reducer ที่ไม่มีนาฬิกาแปลว่าต้องรอ observation ตัวถัดไป **ที่ไม่มีอะไร
  รับประกันว่าจะมี** · ยังไม่ทำโดยตั้งใจ ต้องตัดสินใจก่อนว่าจะยอมให้ `VisitStarted`
  มาช้าแค่ไหน
- **RSSI / ความแรงสัญญาณ** — ไม่ได้อยู่ในโมเดลเลย การเห็นแบบอ่อนมากนับเท่าการเห็น
  แบบชัดเจน (log ปัจจุบันก็ไม่ได้บันทึก RSSI — ADR-11 หัวข้อ 2)
- **ขอบเขตของ `regions` map** — รับ region identifier อะไรก็ได้ ไม่มีการตรวจกับ
  รายการที่ลงทะเบียนไว้ ถ้าผู้เรียกป้อน identifier ที่งอกใหม่เรื่อย ๆ state จะโตไม่หยุด
  (การล้างเมื่อตาบอดเกินเพดานทำให้ map หดได้ แต่ไม่ใช่กลไกที่ตั้งใจให้ทำหน้าที่นี้)
- **ตาบอดที่ตรวจไม่ได้** — ดู [`SENSING.md`](SENSING.md) หัวข้อ 2 · reducer รู้เฉพาะ
  สิ่งที่ผู้เรียกป้อนให้ ตาบอดที่ไม่มีใครตรวจเจอก็ไม่มีใครป้อน

## observation ที่ reducer รับไม่ได้ หรือทำให้ผลไม่แน่นอน

ทุกข้อข้างล่างตรวจด้วยการรันจริง ไม่ใช่การอ่านโค้ดเอา

### 1. 🟢 "มองไม่เห็น" — **แก้แล้วด้วย `SensingLost` / `SensingRestored`**

เดิมไม่มี observation ที่แปลว่า "ตอบไม่ได้ว่าอยู่หรือไม่อยู่" ป้อนสภาพตาบอดเป็น
`RegionNotSeen` แล้ววัดผลจริงได้:

```
เห็น → ตาบอด 10 นาที (ยังนั่งอยู่ที่เดิม) → เห็นอีกครั้ง
  ได้ VisitStarted 2 ครั้ง · ความจริงคือ 1   ← ลูกค้าได้แจ้งเตือนโปรโมชันซ้ำ
```

ตอนนี้นาฬิกา cooldown **หยุดระหว่างตาบอด** และ **ล้างสถานะเมื่อตาบอดเกิน
`blindnessCeiling`** · เทสต์ `บั๊กที่พบจริง` เปรียบเทียบสองทางไว้ในไฟล์เดียวกัน

⚠️ **แต่ยังเหลือกรณีที่ native ตรวจไม่ได้เลย** (force-stop · เครื่องดับ · ระบบทิ้ง
การลงทะเบียนสแกนเงียบ ๆ) ซึ่งจะยังสร้าง visit ปลอมต่อไป — **ห้ามรายงานว่าปัญหา
visit ปลอมถูกแก้แล้ว** ดู [`SENSING.md`](SENSING.md) หัวข้อ 2

### 2. 🔴 เวลาเท่ากันเป๊ะ — ผลขึ้นกับลำดับที่ผู้เรียกป้อน

reducer ไม่มีกติกาตัดสินเสมอ (tiebreak) ในตัว ป้อนสองลำดับนี้ได้ผลคนละอย่าง:

| ลำดับที่ป้อน (เวลาเท่ากันทั้งคู่) | ผล |
|---|---|
| `exit` แล้ว `enter` | การมาเยือนยังเปิดอยู่ |
| `enter` แล้ว `exit` | การมาเยือนถูกปิด |

ยังไม่เกิดกับสองไฟล์ที่มี (**timestamp ซ้ำเป๊ะ 0 คู่ ทั้งสองไฟล์**) แต่ความเสี่ยง
มีจริง: ไฟล์ iOS มีคู่ที่ห่างกัน **น้อยกว่า 1 วินาที 15 คู่** บางคู่ห่างกัน 4
มิลลิวินาที ซึ่ง ADR-11 หัวข้อ 3 ระบุว่าเป็นผลของการที่ระบบ**คิว event ไว้แล้วส่งมา
ติด ๆ กัน** ไม่ใช่การข้ามขอบเขตจริง · ถ้าความละเอียดของ timestamp หยาบลงเมื่อไร
จะกลายเป็นคู่ที่เท่ากันเป๊ะทันที · **ผู้เรียกต้องกำหนดกติกาตัดสินเสมอเอง**

### 3. 🟠 เวลาเดินถอยหลัง — ปฏิเสธทิ้ง และปฏิเสธแบบ**บางส่วน**ได้

`ObservationRejection.timestampWentBackwards` · state ไม่ถูกแก้เลย

สาเหตุที่เกิดได้จริง: เครื่อง sync เวลา · ผู้ใช้ตั้งเวลาเอง · เขตเวลาเปลี่ยนระหว่าง
process · ระบบส่ง event ที่คิวไว้มาสลับลำดับ · และที่อันตรายที่สุดคือ **ผู้เรียกผสม
แหล่งเวลา** — `SystemClock.elapsedRealtime()` ฝั่ง Android รีเซ็ตเมื่อรีบูต ถ้าเอา
ไปปนกับเวลาหน้าปัดจะกลายเป็นการกระโดดถอยหลังหลายชั่วโมง

⚠️ **การป้อนซ้ำทั้งชุดจาก state เดิมถูกปฏิเสธแค่บางตัว** (วัดได้: 1 จาก 4) ตัวที่
เวลาเท่ากับ observation ล่าสุดพอดี**ผ่านเข้าไป** ผลที่ได้จึงเป็นสถานะลูกผสมที่ผิด
โดยไม่มีอะไรฟ้อง — **เล่นซ้ำต้องเริ่มจาก `VisitFilterState.initial` เสมอ**

ผลของการทิ้ง observation: ทิ้ง `RegionNotSeen` → การมาเยือนเปิดค้างนานเกินจริง ·
ทิ้ง `RegionSeen` → หลักฐานไม่ถูกต่ออายุ การมาเยือนอาจถูกปิดแล้วครั้งถัดไปกลายเป็น
`VisitStarted` เกินมาหนึ่งครั้ง

### 4. 🟠 ไม่มีใครป้อนอะไรเลย → `VisitEnded` ไม่มากี่โมงก็ไม่รู้

นี่คือ**ราคาที่จ่ายเพื่อไม่ต้องมี `Timer`** ไม่ใช่บั๊ก · reducer รู้ว่าการมาเยือนจบ
ก็ต่อเมื่อมีคนป้อนเวลาเข้ามา วัดได้: หลัง `RegionNotSeen` แล้วไม่ป้อนอะไรอีกเลย
การมาเยือนยังค้างอยู่ใน state และไม่มี `VisitEnded` ออกมา

บนอุปกรณ์จริงแปลว่า: force-stop · นาฬิกาปลุกถูกล้าง · ระบบไม่ปลุก process อีกเลย
→ การมาเยือนค้างอยู่ในไฟล์ state ไปเรื่อย ๆ · **`VisitEnded` มาช้าได้ไม่จำกัด แต่
`endedAt` ยังถูกต้องเสมอ** เพราะรายงานหลักฐานสุดท้ายที่เห็น ไม่ใช่เวลาที่รู้ตัว

**ข้อบังคับกับผู้เรียก:** ป้อน `TimeAdvanced` ทุกครั้งที่ถูกปลุก ไม่ว่าด้วยสาเหตุใด

### 5. 🟡 `RegionSeen` เป็น observation แรกของ region → เวลาที่มาถึงไม่รู้

ได้ `evidence = alreadyInsideAtFirstObservation` และ `at` เป็น**ขอบบน**ของเวลาที่
มาถึง · **เกิดกับไฟล์ Android จริง** (บรรทัด event แรกคือ `enter` ไม่มี `exit` นำ)

ผู้เรียกที่รู้แน่ว่าเพิ่งเริ่มเฝ้า region และยังไม่เคยเห็นอะไร **ควรป้อน
`RegionNotSeen` ก่อนหนึ่งครั้ง** เพื่อให้ครั้งถัดไปเป็น `arrivalObserved` —
แต่ป้อนได้ก็ต่อเมื่อมันจริงเท่านั้น ไม่งั้นคือการสร้างหลักฐานปลอม

### 6. 🟡 ไม่มี observation สำหรับ "เลิกเฝ้า region นี้แล้ว"

`regions` map ไม่มีวันหดเอง ผู้เรียกต้องลบ entry ทิ้งเอง — ไม่งั้น `TimeAdvanced`
จะยังไล่ตัดสิน region ที่ไม่ได้เฝ้าแล้วต่อไปเรื่อย ๆ

### 7. 🟢 รับได้ ไม่มีปัญหา

`exit` ที่ไม่เคยมี `enter` นำหน้า (บรรทัดแรกของไฟล์ iOS) · `exit` ซ้ำติดกัน ·
`RegionSeen` ซ้ำระหว่างการมาเยือนเดียวกัน · `ObservationsEnded` ซ้ำ ·
`ObservationsEnded` ตอนไม่มีการมาเยือนเปิดค้าง
