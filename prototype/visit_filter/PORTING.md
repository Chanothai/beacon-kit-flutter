# พอร์ตไป Kotlin และ Swift — จุดที่ **ไม่ตรงกัน** และวิธีกันไม่ให้เพี้ยน

> **สถานะ:** ตัดสินใจแล้วว่าตรรกะนี้ต้องทำงานฝั่ง native ทั้งสองแพลตฟอร์ม เพราะต้อง
> ยิงแจ้งเตือนตอนแอปปิดอยู่ · **เวอร์ชัน Dart ในโฟลเดอร์นี้เป็นข้อกำหนดอ้างอิงและ
> ชุดเทสต์ต้นแบบ ไม่ใช่โค้ดที่จะรันบนเครื่องผู้ใช้**

ทุกข้อข้างล่างคือจุดที่ **โค้ดที่แปลตรงตัวแล้วดูถูกต้อง จะให้ผลต่างกันจริง**
ไม่ใช่ความต่างเชิงสไตล์

## 🔴 ระดับที่ทำให้ผลไม่ตรงกันแน่นอน

### 1. `DateTime` / `Date` / `Instant` — Swift `Date` เป็นทศนิยม

`Date` ของ Swift เก็บเป็น `TimeInterval` = `Double` วินาที · ค่ามิลลิวินาทีจำนวน
มาก**แทนไม่ได้เป๊ะ** การเทียบ `endedAt == expected` จึงกลายเป็นการเทียบทศนิยม และ
`TimeInterval` กับ `java.time.Duration` ก็คนละความละเอียดกัน

**สิ่งที่ต้องทำ:** ในทั้งสามภาษา เวลาภายใน reducer ต้องเป็น **จำนวนเต็มมิลลิวินาที
นับจาก epoch** — Dart `int` · Kotlin `Long` · Swift `Int64` · แปลงเป็นชนิดวันเวลา
ของแพลตฟอร์ม**ที่ขอบเท่านั้น**

ไฟล์ `vectors.json` บังคับกติกานี้อยู่แล้ว: `encodeTime()` โยน `ArgumentError` ถ้า
เจอเศษต่ำกว่ามิลลิวินาที และมีเทสต์ตรวจว่าทั้งไฟล์ไม่มีเลขทศนิยมสักตัว

⚠️ **เวอร์ชัน Dart ปัจจุบันยังใช้ `DateTime` ใน API สาธารณะ** — เป็นหนี้ที่รู้ตัว
ถ้าจะให้ข้อกำหนดอ้างอิงตรงกับ port 100% ต้องเปลี่ยน `DateTime` เป็น `int` ทั้งชั้น
(เลขในไฟล์ vector ไม่เปลี่ยน เปลี่ยนแค่ชนิดใน API) — **ยังไม่ทำ รอตัดสิน**

### 2. ลำดับของ `Map` — `Dictionary` ของ Swift ไม่มีลำดับ **และเปลี่ยนทุกครั้งที่รัน**

`Dictionary` ของ Swift ใช้ hash ที่ seed ใหม่ทุก process ลำดับ `for (k, v) in dict`
จึงต่างกันได้ระหว่างการรันสองครั้งของ**ไบนารีตัวเดียวกัน** ส่วน Dart `Map` และ
Kotlin `LinkedHashMap` เรียงตามลำดับที่ใส่

โค้ด Dart จัดการไว้แล้วด้วยการ **เรียงตาม identifier ก่อนไล่ทุกครั้ง**
(`_settleAll`, `_closeOpenVisitsAtEdge`) — **ห้ามตัดขั้นตอนนี้ทิ้งตอนพอร์ต** และ
ฝั่ง Kotlin **ห้ามใช้ `HashMap`** (ใช้ `LinkedHashMap` หรือเรียงทุกครั้ง)

เคส `multi-region-settle-order` ในไฟล์ vector มีไว้จับข้อนี้โดยเฉพาะ

### 3. การเรียงสตริง — Swift เรียงตาม Unicode ส่วน Dart/Kotlin เรียงตาม UTF-16

| ภาษา | `"ก" < "a"` ตัดสินจาก |
|---|---|
| Dart `String.compareTo` | ลำดับ UTF-16 code unit |
| Kotlin `String.compareTo` | ลำดับ UTF-16 code unit |
| **Swift `<`** | **ลำดับตาม Unicode canonical** |

ตราบใดที่ region identifier เป็น ASCII ล้วน (`k9p-default`) ทั้งสามให้ผลเดียวกัน
**แต่ระบบนี้มีชื่อสาขาเป็นภาษาไทยเต็มไปหมด** ถ้าวันหนึ่ง identifier กลายเป็น
`สาขา-รัชดา` ลำดับการตัดสิน region จะต่างกันระหว่าง iOS กับ Android ทันที

**เสนอ:** บังคับให้ region identifier เป็น `[a-z0-9_-]` เท่านั้น (ตรวจตอนลงทะเบียน)
— ถูกกว่าและตรวจง่ายกว่าการไปทำ byte-wise comparator สามภาษา

### 4. `assert` ของ Dart ถูกถอดทิ้งใน release · `require`/`precondition` ไม่ถูกถอด

เดิมโค้ดใช้ `assert(cooldown > Duration.zero)` ซึ่งแปลว่า **บน release build ของ
Dart ค่าที่ผิดจะผ่านไปเงียบ ๆ แต่ port ทั้งสองจะ crash** — ความต่างที่หาไม่เจอที่สุด

**แก้แล้วในรอบนี้:** เปลี่ยนเป็น `throw ArgumentError` ซึ่งทำงานเสมอ
· Kotlin ใช้ `require()` · Swift ใช้ `precondition()` **ห้ามใช้ `assert()` ของ Swift**
(ถูกถอดใน `-O` เช่นกัน)

## 🟠 ระดับที่พลาดง่ายตอนพอร์ต

### 5. `data class` ของ Kotlin สร้าง `equals` ให้อัตโนมัติ — และนั่นคือปัญหา

`equals`/`hashCode` ของ `data class` ครอบ **พารามิเตอร์ใน constructor เท่านั้น**
ไม่ครอบ property ที่ประกาศในบอดี้ · ส่วน Dart เขียนมือจึงต้องตามแก้เอง

ผลคือ **ทั้งสองทางเพี้ยนได้:** เพิ่มฟิลด์ใน Kotlin แล้ว `equals` เปลี่ยนเองโดยไม่มี
ใครสังเกต · เพิ่มฟิลด์ใน Dart แล้วลืมใส่ใน `==` · ไฟล์ vector จับได้เพราะเทียบทีละ
ช่องจาก JSON ไม่ได้เทียบด้วย `==` ของภาษา

### 5.5 ผิวสัมผัสที่โตขึ้นจาก `SensingLost` — enum เพิ่มสี่ตัว

`SensingLossCause` (5 ค่า) · `SensingStatus` (3 ค่า) · `VisitEndReason` (เพิ่มเป็น
3 ค่า) · `VisitStartEvidence` (2 ค่า) — ทั้งหมดถูกเข้ารหัสในไฟล์ vector ด้วย
**ชื่อค่าเป็นสตริง** ไม่ใช่ลำดับตัวเลข เพราะการเรียงลำดับสมาชิก enum ต่างกัน
ระหว่างสามภาษาได้ง่ายมากและจะเพี้ยนแบบเงียบสนิท

⚠️ **`SensingStatus.lostBeyondCeiling` เป็นสถานะที่มองข้ามง่ายที่สุดตอนพอร์ต** —
ถ้าพอร์ตเป็น `Bool isBlind` ธรรมดา การล้างสถานะจะเกิดซ้ำทุก observation ระหว่างที่
ยังตาบอดอยู่ · เคส `ล้างครั้งเดียวต่อหนึ่งช่วงตาบอด` จับข้อนี้

### 6. `sealed class` → Kotlin `sealed` · Swift **`enum` เท่านั้น**

Swift ได้ความครบถ้วนของ `switch` ตอน compile **เฉพาะกับ `enum` ที่มี associated
value** · ถ้าพอร์ต `VisitObservation` เป็น protocol หรือ class hierarchy จะไม่มีใคร
เตือนเมื่อเพิ่มชนิดใหม่แล้วลืมจัดการ — ซึ่งเป็นวิธีที่ตรรกะจะเพี้ยนแบบเงียบที่สุด

### 7. `SharedPreferences.apply()` ทำให้ state หายบน Android

`apply()` เขียนแบบ **asynchronous** · กระบวนการที่ถูกปลุกมาเพื่อ `onReceive` มีอายุ
หลักสิบมิลลิวินาที การเขียนอาจไม่ทันลงดิสก์ก่อน process ตาย **โดยไม่มีอะไรฟ้อง**

**ต้องใช้ `commit()`** (synchronous, คืน `Boolean`) แล้ว**ตรวจค่าที่คืนมา** — นี่เป็น
ผลโดยตรงจากเหตุผลเดียวกับที่ห้ามใช้ `Timer` และเป็นจุดที่ port จะพังต่างจาก Dart
ที่เทสต์ในหน่วยความจำล้วน

### 8. การแปลงเวลาจากไฟล์หลักฐาน

- **Swift:** `ISO8601DateFormatter` **ไม่รองรับเศษวินาทีถ้าไม่ใส่
  `.withFractionalSeconds`** — ไฟล์หลักฐานมีมิลลิวินาทีทุกบรรทัด ถ้าลืมจะ parse
  ไม่ผ่านทั้งไฟล์ หรือแย่กว่านั้นคือปัดทิ้งเงียบ ๆ
- **Android:** ห้ามใช้ `SimpleDateFormat` (ขึ้นกับ locale และ timezone ปริยาย)
  ใช้ `OffsetDateTime.parse` · และ **ห้ามใช้ `String.format` ด้วย locale ปริยาย**
  เมื่อเขียนตัวเลขกลับลงไฟล์ เพราะ locale ไทยทำให้ได้เลขไทย (`๑๒๓`)
  — ใช้ `Locale.ROOT` เสมอ

### 9. `identical()` ใน `_settleOne`

เป็นทางลัดเลี่ยงการ copy map เมื่อไม่มีอะไรเปลี่ยน · Swift `struct` ไม่มี identity
ให้เทียบ · **แปลตรงตัวไม่ได้แต่แปลความหมายได้** — เทียบค่าแทน หรือให้ `_settle`
คืนธงบอกว่ามีการเปลี่ยนหรือไม่ · ไม่กระทบผลลัพธ์ กระทบแค่ประสิทธิภาพ

## 🟡 ตรวจแล้วว่าไม่เป็นปัญหา — บันทึกไว้กันตรวจซ้ำ

- **ขนาดจำนวนเต็ม:** epoch มิลลิวินาทีตอนนี้ ~1.79 × 10¹² เล็กกว่า 2⁵³ มาก จึงแทน
  ได้เป๊ะแม้ผ่าน `Double` ของ JSON · `Int64` ทั้งสามภาษาไม่ล้น
- **เขตเวลา:** reducer ไม่แตะเขตเวลาเลย คำนวณบนช่วงเวลาสัมบูรณ์ล้วน · เรื่องเขตเวลา
  อยู่ที่ตัวอ่าน/ตัวเขียน log เท่านั้น (`+07:00` — ดู `GROUND_TRUTH.md`)
- **การหารจำนวนเต็ม:** reducer ไม่มีการหารเลย มีแต่ในเครื่องมือ `cooldown_sweep`

## วิธีกันไม่ให้สามที่นี้เพี้ยนจากกัน

**หลักการ: ย้ายสัญญาออกจากโค้ดไปไว้ใน "ข้อมูล" ที่ทั้งสามภาษาอ่านไฟล์เดียวกัน**
ถ้าสัญญาอยู่ในโค้ด Dart การเทียบว่าตรงกันไหมต้องใช้คนอ่านสามภาษาพร้อมกัน ซึ่งไม่มี
วันเกิดขึ้นจริงหลังผ่านไปสามเดือน

### ชั้นที่ 1 — ไฟล์ conformance vector (ทำแล้ว)

`spec/visit_filter/vectors.json` · **24 เคส** · สร้างด้วย
`dart run bin/generate_vectors.dart` · **commit ไฟล์นี้เสมอ มันคือสัญญา ไม่ใช่
build artifact**

แต่ละเคสมีครบ: `cooldownMs` · `blindnessCeilingMs` · `initialState` ·
`observations` (หรือ `logFile`) ·
`expectedEvents` · `expectedRejections` · `expectedFinalState` · และ `why` ที่บอกว่า
เคสนี้กันอะไรไม่ให้พัง เพื่อให้คนรีวิว diff อ่านออกว่าอะไรเปลี่ยน

เวลาทุกค่าเป็น **จำนวนเต็มมิลลิวินาที** ตามข้อ 1 · `formatVersion` ขึ้นเลขเมื่อ
**โครงสร้างไฟล์**เปลี่ยน ไม่ใช่เมื่อค่าที่คาดหวังเปลี่ยน

### ชั้นที่ 2 — ไฟล์หลักฐานจริงสองคืนเป็นเกณฑ์รับ end-to-end (ทำแล้ว)

สองเคสสุดท้ายในไฟล์ vector ไม่ได้ฝัง observation ไว้ แต่**อ้างเส้นทางไฟล์ log**
ทั้งสามภาษาจึงอ่านไฟล์เดียวกันจริง ๆ — ซึ่งแปลว่า **ตัวอ่านไฟล์ log ของทั้งสามภาษา
ก็ถูกทดสอบไปด้วย** (ข้อ 8 ข้างบนจะถูกจับตรงนี้)

เกณฑ์ยังเป็นอันเดิมจาก `docs/test-data/GROUND_TRUTH.md`: **`VisitStarted` ไฟล์ละ 1
ครั้ง ด้วย cooldown ค่าเดียวกัน**

### ชั้นที่ 3 — เทสต์ที่ล้มเมื่อไฟล์ vector เก่า (ทำแล้ว)

`test/conformance_test.dart` สร้างเอกสาร vector ใหม่จากโค้ดปัจจุบันแล้วเทียบกับไฟล์
ที่ commit ไว้ · **แก้พฤติกรรมแล้วไม่ regenerate = เทสต์ล้มทันที** · regenerate
แล้ว diff จะโผล่ใน PR ให้คนรีวิวเห็นว่าสัญญาเปลี่ยนตรงไหน

### ชั้นที่ 4 — สิ่งที่ยังต้องทำเมื่อเขียน port

1. **Kotlin:** เทสต์หนึ่งตัวที่อ่าน `vectors.json` ไฟล์เดิม (คัดลอกหรือ symlink เข้า
   `src/test/resources`) แล้วเล่นทุกเคส · **ห้ามคัดลอกค่าที่คาดหวังไปเขียนใหม่ใน
   Kotlin** เพราะนั่นคือการสร้างสัญญาชุดที่สอง
2. **Swift:** เทสต์เดียวกันใน `RunnerTests` อ่านไฟล์เดิม
3. **CI:** สาม job (`dart test` · `gradlew test` · `xcodebuild test`) ต้อง**เขียว
   พร้อมกัน** ก่อน merge · job ไหนล้มคือสัญญาแตก
4. **กติกาการรีวิว:** PR ที่แตะพฤติกรรมของชั้นกรอง **ต้องแตะทั้งสามที่ใน PR เดียว**
   ถ้าแตะที่เดียวได้โดย CI ยังเขียว แปลว่ากลไกนี้มีรูและต้องเพิ่มเคสก่อน
5. **`formatVersion`:** ตัวอ่านทั้งสามภาษาต้องล้มถ้าเจอเลขที่ไม่รู้จัก — ไม่ใช่
   ข้ามฟิลด์ที่ไม่รู้จักไปเงียบ ๆ

### สิ่งที่กลไกนี้ยัง**จับไม่ได้**

- **พฤติกรรมที่ไม่มีเคสครอบ** — vector จับได้เฉพาะสิ่งที่มีเคส · เคสใหม่ต้องเพิ่ม
  พร้อมกับพฤติกรรมใหม่เสมอ ไม่ใช่เพิ่มทีหลัง
- **เรื่องที่เกิดเฉพาะบนเครื่องจริง** — `commit()` vs `apply()` (ข้อ 7) ·
  process ตายกลางคัน · นาฬิกาปลุกไม่ดัง · ไม่มี vector ไหนจับได้ ต้องอาศัย runbook
  และการทดสอบบนอุปกรณ์จริงเท่านั้น
- **การเรียงสตริงที่ไม่ใช่ ASCII** (ข้อ 3) — จะจับได้ก็ต่อเมื่อเพิ่มเคสที่มี
  identifier ภาษาไทยเข้าไป · **ยังไม่ได้เพิ่ม** เพราะยังไม่ตัดสินว่าจะบังคับ ASCII
