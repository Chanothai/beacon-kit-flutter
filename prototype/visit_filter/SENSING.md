# `SensingLost` / `SensingRestored` — observation ชนิด "ตอบไม่ได้"

## 1. ชื่อและความหมาย — ต่างจาก `RegionNotSeen` อย่างไร

| | `RegionNotSeen` | `SensingLost` |
|---|---|---|
| ประโยคที่มันพูด | "**แพลตฟอร์มยืนยันว่าไม่อยู่ในโซนแล้ว**" | "**เราตาบอด ตอบไม่ได้ว่าอยู่หรือไม่อยู่**" |
| เป็นหลักฐานของ | ตำแหน่งของผู้ใช้ | ความสามารถของเรา — **ไม่ได้พูดถึงผู้ใช้เลย** |
| ขอบเขต | region เดียว | **ทุก region พร้อมกัน** (Bluetooth ที่ปิดอยู่บังทุกสาขาเท่ากัน) |
| นาฬิกา cooldown | เดินต่อ | **หยุด** |
| ใครเป็นคนบอก | ระบบ (`didExitRegion` / นาฬิกาปลุกของเรา) | เราเป็นคนตรวจเอง |

ชื่อจงใจไม่มีคำว่า `Region` อยู่ในนั้น เพราะมันไม่ได้ผูกกับ region ใด และจงใจใช้คำว่า
`Sensing` (ความสามารถในการรับรู้) ไม่ใช่ `Monitoring` (ซึ่งในโค้ดนี้หมายถึงการ
ลงทะเบียนเฝ้า region ที่ยังลงทะเบียนอยู่ดีแม้ Bluetooth จะปิด)

`SensingRestored` ปิดช่วง — **ช่วงระหว่างสองตัวนี้ถูกหักออกจากความเงียบ** เท่ากับ
"หยุดนาฬิกาแล้วเดินต่อ" ไม่ใช่ "รีเซ็ตนาฬิกา"

`SensingLossCause` (`bluetoothOff` · `locationServicesOff` · `permissionRevoked` ·
`scanRegistrationLost` · `unknown`) เป็น **สัญญาณดิบล้วน ไม่มีผลกับการตัดสินใจ** —
ทุกสาเหตุหยุดนาฬิกาเหมือนกันหมด เก็บไว้เพื่อให้ไฟล์หลักฐานตอบได้ว่าช่วงตาบอดแต่ละ
ช่วงมาจากอะไร

### กติกาที่ตามมา

- **หักเฉพาะส่วนที่ทับกับความเงียบจริง** — ตาบอดตั้งแต่ก่อน region นั้นจะเงียบ
  ส่วนที่อยู่ก่อนหน้าไม่ได้ถูกใครกินไป จึงไม่ต้องคืน
- **`SensingLost` ซ้ำไม่เลื่อนจุดเริ่ม** — หลักการเดียวกับ `exit` ซ้ำ ถ้าเลื่อนได้
  เพดานจะไม่มีวันถึงเมื่อระบบยิงถี่กว่าเพดาน
- **เกิน `blindnessCeiling` → ล้างสถานะทิ้งทั้งหมด** ปิดการมาเยือนที่เปิดค้างด้วย
  `VisitEndReason.sensingLostBeyondCeiling` แล้ว **ลบ entry ของ region ทิ้ง** ไม่ใช่
  ตั้งเป็น "ไม่อยู่" — เพราะเราตอบไม่ได้ว่าอยู่หรือไม่อยู่ · ผลคือครั้งหน้าที่เห็น
  beacon จะได้ `alreadyInsideAtFirstObservation` ซึ่งตรงกับความจริงว่าเราไม่เคยเห็น
  การมาถึง
- **ล้างครั้งเดียวต่อหนึ่งช่วงตาบอด** (`SensingStatus.lostBeyondCeiling`) มิฉะนั้น
  การมาเยือนที่เพิ่งเปิดระหว่างยังตาบอดอยู่จะถูกล้างซ้ำทุก observation
- **`blindnessCeiling` ไม่มีค่า default** — ยังไม่มีข้อมูลสนามสำหรับตั้งค่านี้เลย
  log สองคืนที่มีอยู่ **ไม่มีช่วงตาบอดที่ตรวจได้แม้แต่ช่วงเดียว** เพราะบิลด์ที่เก็บ
  log ยังไม่มีการตรวจ

## 2. ฝั่ง native จะรู้ได้อย่างไรว่าตอนนี้ตาบอด

> **ข้อนี้ตัดสินว่า observation นี้มีประโยชน์จริงหรือเป็นแค่ของประดับ** — ถ้า native
> ตรวจไม่ได้ ก็ไม่มีใครป้อน และ reducer ก็ไม่มีทางรู้

### รูปแบบการตรวจที่เข้ากับสถาปัตยกรรมของเรา: **poll ตอนถูกปลุก ไม่ใช่ subscribe**

เราไม่มี process ที่มีชีวิตอยู่แล้ว (ADR-14) การ subscribe callback จึงไม่ใช่ทาง —
ทางที่ตรงกับของจริงคือ **ทุกครั้งที่ `BeaconScanReceiver` / `RegionExitAlarmReceiver`
/ `BootCompletedReceiver` ถูกเรียก ให้อ่านสถานะปัจจุบันก่อน แล้วป้อน
`SensingLost`/`SensingRestored` ก่อน observation จริงของรอบนั้น**

⚠️ **ผลข้างเคียงที่ต้องยอมรับ:** การ poll บอกได้แค่ "ตอนนี้ตาบอด" **ไม่ได้บอกว่าเริ่ม
ตาบอดตอนไหน** · `SensingLost.at` จึงเป็นเวลาที่เราตื่นมาเห็น ไม่ใช่เวลาที่มันเริ่มจริง
เราจะ **หักเวลาน้อยกว่าที่ควร** ทุกครั้ง ซึ่งทำให้ความเงียบดูยาวเกินจริง —
**เอนไปทางเกิด visit ปลอม ไม่ใช่เอนไปทางปลอดภัย** · ความถี่ที่เราถูกปลุกจึงกำหนด
โดยตรงว่าจะเหลือ visit ปลอมเท่าไร

### Android

| อาการ | ตรวจด้วย | สถานะ |
|---|---|---|
| Bluetooth ปิด | `BluetoothAdapter.isEnabled` | ✅ **ใช้อยู่แล้วในรีโปนี้** — `BeaconKitAndroidPlugin.kt:277` และ `BackgroundRegionMonitor.kt:199` |
| สิทธิ์ถูกถอน | `Context.checkSelfPermission` ตอนที่โค้ดรัน | ✅ ตรวจได้ทุกครั้งที่เราถูกปลุก |
| Location services ปิดทั้งเครื่อง | `LocationManager.isLocationEnabled` | 🔶 **ยังไม่ได้ยืนยันกับเอกสาร** — อยู่ในรายการ "หาแหล่งอ้างอิงไม่ได้" ของ `docs/sources/android_background_ble.md` |
| รู้เวลาที่ Bluetooth ถูกปิด **จริง ๆ** | `BluetoothAdapter.ACTION_STATE_CHANGED` | 🛑 **ยืนยันแล้วว่าใช้ไม่ได้** — ดูข้างล่าง |

### 🛑 `ACTION_STATE_CHANGED` ใน manifest — **ยืนยันแล้วว่าไม่ได้รับ**

*(หลักฐานคำต่อคำ + URL: `docs/sources/android_background_ble.md` หัวข้อ 9)*

`android.bluetooth.adapter.action.STATE_CHANGED` เป็น implicit broadcast และ
**ไม่ปรากฏในหน้ารายการข้อยกเว้นของ Android เลย** (ไล่ทั้งหน้าแล้ว — Bluetooth มีอยู่
แค่ `BluetoothHeadset` / `BluetoothA2dp` `ACTION_CONNECTION_STATE_CHANGED` และ
`ACTION_ACL_CONNECTED` / `ACTION_ACL_DISCONNECTED`) ตัวรับที่ประกาศใน manifest จึงไม่
ถูกเรียกบนแอปที่ target API 26 ขึ้นไป

เอกสารเสนอทางเดียวคือ `Context.registerReceiver()` ตอนรัน ซึ่ง **ผูกกับ `Context` ที่
มีชีวิต** — ขัดกับข้อเท็จจริงที่ ADR-14 ทั้งฉบับตั้งอยู่บนมัน

> **สรุป: ฝั่ง Android เราจะไม่มีวันรู้เวลาที่เริ่มตาบอด รู้ได้แค่ว่า "ตอนที่ตื่นมา
> ตาบอดอยู่"** · การ poll ตอนถูกปลุกไม่ใช่ทางเลือกที่ดีที่สุด มันคือ**ทางเดียว**

### เพียงพอไหม — และเหลือข้อจำกัดอะไร

**เพียงพอในแง่ที่ว่าไม่มีทางอื่น** และครอบสาเหตุที่พบบ่อยที่สุด (Bluetooth ปิด /
สิทธิ์ถูกถอน) ได้จริง แต่ต้องระบุข้อจำกัดสามข้อทุกครั้งที่อ้างถึง:

1. **ความละเอียดของการ poll = คาบที่เราถูกปลุก** และตอนตาบอด **แหล่งปลุกหลักตายไป
   พร้อมกัน** — ผลสแกนหยุดส่งเพราะ Bluetooth ปิด เหลือแต่นาฬิกาปลุก exit ของเราเอง
   ซึ่ง ADR-15 วัดได้ว่า `AlarmManager` เลื่อนไปเกาะกลุ่มที่ **10 นาที ×21 และ
   15 นาที ×11** · **ช่องว่างที่เรามองไม่เห็นจึงกว้างระดับสิบนาที ไม่ใช่วินาที**
2. **เวลาที่รายงานเอนไปทางผิด** — `SensingLost.atMs` เป็นเวลาที่ตื่นมาเห็น ซึ่ง
   **ช้ากว่า**เวลาที่เริ่มจริงเสมอ ทำให้หักเวลาน้อยกว่าที่ควร → **เอนไปทางสร้าง
   visit ปลอม ซึ่งเป็นบั๊กเดิมที่เรากำลังแก้** · หัวข้อ 5 เสนอวิธีกลับทิศอคตินี้
3. **สาเหตุที่ตรวจไม่ได้ยังตรวจไม่ได้เหมือนเดิม** — force-stop · เครื่องดับ ·
   ระบบทิ้งการลงทะเบียนสแกนเงียบ ๆ (ดูรายการข้างล่าง)

### iOS

*(หลักฐานคำต่อคำ + URL: `docs/sources/ios_sensing_availability.md`)*

| อาการ | ตรวจด้วย | สถานะ |
|---|---|---|
| Bluetooth ปิด | `CBCentralManagerDelegate.centralManagerDidUpdateState` → `.poweredOff` | ✅ **มีโค้ดนี้อยู่แล้ว** — `RawAdvertisementScanner.swift:92` |
| **สิทธิ์** Bluetooth โดยไม่ต้องสร้าง instance | `CBManager.authorization` (class property, iOS 13.1+) | ✅ **ยืนยันแล้ว** — เอกสารระบุเอง: *"You can also use it to check the app's authorization status **before creating a `CBManager` instance**."* · ⚠️ ตอบเรื่อง**สิทธิ์เท่านั้น ไม่ได้บอกว่า Bluetooth เปิดอยู่หรือไม่** |
| region monitoring ล้มเหลว | `locationManager(_:monitoringDidFailFor:withError:)` | ✅ ยืนยันว่ามีและทำอะไร — แต่เอกสารบอกแค่ *"a more general failure in configuring the region monitoring service"* **ไม่ได้แจกแจงว่าอะไรบ้าง** ห้ามอ้างว่าจะถูกเรียกตอนปิด Bluetooth |
| สิทธิ์ location เปลี่ยน | callback แจ้งการเปลี่ยน authorization ของ `CLLocationManager` | 🔶 ยังไม่ได้ดึงชื่อ selector มายืนยัน |

### ✅ ปิด alert ตอนสร้าง `CBCentralManager` ได้ — ยืนยันชื่อคีย์แล้ว

`RawAdvertisementScanner` สร้าง `CBCentralManager` แบบ lazy โดยตั้งใจ
(`RawAdvertisementScanner.swift:17-18`) เพราะการสร้างมันขึ้นมาเพื่อ*ถาม*สถานะมี
ผลข้างเคียงคือระบบเตือนผู้ใช้ · คีย์ที่ปิด alert นั้นคือ:

```swift
let CBCentralManagerOptionShowPowerAlertKey: String
```

> "A Boolean value that specifies whether the system warns the user if the app
> instantiates the central manager when Bluetooth service isn't available."
>
> "The value for this key is an NSNumber object. **If the key isn't specified, the
> default value is true.**"
>
> — https://developer.apple.com/documentation/corebluetooth/cbcentralmanageroptionshowpoweralertkey

**ค่าปริยายคือ `true`** → โค้ดที่ไม่ส่ง option นี้จะเตือนผู้ใช้จริง · ค่าที่ใส่ต้องเป็น
`NSNumber`

⚠️ เอกสาร **ไม่ได้ระบุ**ว่าตั้ง `false` แล้ว `centralManagerDidUpdateState` ยังถูกเรียก
ครบเหมือนเดิมหรือไม่ — สมเหตุสมผลว่าได้ แต่ไม่มีประโยคไหนรับรอง **ต้องวัดเอง**

### 🛑 คำถามฝั่ง iOS ที่สำคัญกว่าทั้งหมดนี้ และยังตอบไม่ได้

**เมื่อผู้ใช้ปิด Bluetooth ระหว่างที่เฝ้า `CLBeaconRegion` อยู่ CoreLocation ยิง
`didExitRegion` ให้หรือไม่**

ถ้ายิง ฝั่ง iOS จะเจอบั๊ก visit ปลอมแบบเดียวกัน **และ `SensingLost` ช่วยไม่ได้เลยถ้า
`didExitRegion` มาถึงก่อนที่เราจะรู้ตัวว่าตาบอด** · ค้นเอกสารแล้วไม่พบประโยคที่ระบุ
พฤติกรรมนี้ — **ต้องวัดบนเครื่องจริงเป็นเคสแรกของรอบทดสอบ iOS รอบหน้า**

### 🛑 กรณีที่ **รู้ไม่ได้เลย** — ทั้งสองแพลตฟอร์ม

1. **force-stop / เครื่องดับ** — ไม่มีโค้ดของเรารันเลย ป้อน `SensingLost` ไม่ได้
   และตอนกลับมาก็ตอบไม่ได้ว่าหายไปนานเท่าไรเพราะอะไร · ช่องว่างนี้ปรากฏเป็น
   "ความเงียบ" ธรรมดา → **ยังได้ visit ปลอม**
   · บรรเทาได้บางส่วนด้วยการเทียบเวลาหน้าปัดกับ `SystemClock.elapsedRealtime()`
   ตอน process เกิดใหม่เพื่อรู้ว่าเครื่องเพิ่งบูต **แต่ยังตอบไม่ได้ว่าเริ่มตาบอด
   ตอนไหน** และเวลาที่เดินถอยหลังจะถูก reducer ปฏิเสธ
2. **ระบบทิ้งการลงทะเบียนสแกนเงียบ ๆ** — `startScan(..., PendingIntent)` ไม่มี
   callback บอกว่าถูกยกเลิก (`docs/sources/android_background_ble.md`)
3. **แบต beacon หมด / beacon ถูกย้าย** — เหมือน "ลูกค้าเดินออกไป" ทุกประการ
   ไม่ใช่การตาบอดที่ตรวจได้
4. **สัญญาณถูกบัง** — มือถืออยู่ในกระเป๋า คนยืนบัง ตู้เหล็ก · RSSI ตกต่ำกว่าเกณฑ์
   โดยไม่มีสัญญาณใดแยกออกจากการเดินออกไป
5. **Doze / app standby** — ระบบหน่วงการส่งผลโดยไม่มี callback (ADR-14 หัวข้อ 2.4)

> **ห้ามรายงานว่าปัญหา visit ปลอมถูกแก้แล้ว** — observation นี้ครอบได้เฉพาะ
> "ตาบอดที่ระบบยอมบอกเรา" · ข้อ 1 กับ 2 จะยังสร้าง visit ปลอมต่อไป

### สิ่งที่ผู้เรียกต้องทำเพิ่ม

- **เก็บ `sensing` / `sensingLostAt` ลงที่เดียวกับ state ที่เหลือ** — มันเป็นส่วนหนึ่ง
  ของ `VisitFilterState` และหายไปพร้อม process เหมือนกัน
- **ตอน process เกิดใหม่ขณะที่ state บอกว่าตาบอดอยู่** ต้องอ่านสถานะปัจจุบันแล้ว
  ป้อน `SensingRestored` ด้วยเวลาปัจจุบันถ้ามองเห็นแล้ว — ⚠️ วิธีนี้ **หักเวลาเกินจริง**
  ถ้าความสามารถกลับมาตั้งแต่ตอนที่เราตายอยู่ · เป็นหนี้ที่รู้ตัว ไม่มีทางแก้จากใน
  reducer

## 3. เคสที่เพิ่มเข้าไฟล์ vector

| เคส | ครอบอะไร |
|---|---|
| `blindness-pauses-cooldown-below-ceiling` | **บั๊กที่พบจริง** — ปิด Bluetooth 10 นาทีขณะอยู่ที่เดิม ต้องได้ `VisitStarted` 1 ครั้ง |
| `blindness-beyond-ceiling-resets` | เกินเพดาน → `sensingLostBeyondCeiling` + ล้าง state + ครั้งหน้าเป็น `alreadyInside` |
| `blindness-exactly-at-ceiling-resets` | **ขอบพอดี** — เกณฑ์ `>=` เหมือน cooldown |
| `blindness-one-millisecond-below-ceiling` | **อีกฝั่งของขอบ** — ขาด 1 มิลลิวินาที ต้องหักเวลา ไม่ใช่ล้างทิ้ง |
| `blindness-straddles-cooldown-expiry` | ตาบอดคาบเกี่ยวจังหวะที่ cooldown จะครบ — ห้ามปิดระหว่างตาบอด และหลังกลับมาต้องนับเวลาที่เหลือต่อ |
| `blindness-starts-while-still-present` | ตาบอดก่อนแล้วค่อยได้ `exit` — หักเฉพาะส่วนที่ทับ |
| `repeated-sensing-lost-does-not-move-ceiling` | `SensingLost` ซ้ำไม่เลื่อนเพดาน |
| `blindness-with-no-open-visit-emits-nothing` | ตาบอดตอนไม่มีการมาเยือนเปิดค้าง — เงียบสนิท |

ไม่เปลี่ยนแม้แต่ช่องเดียว — **สองไฟล์นี้ไม่มี `SensingLost` อยู่เลย** เพราะบิลด์ที่
เก็บ log ยังไม่มีการตรวจว่าตาบอด · `blindnessCeiling` จึงไม่มีผลกับทั้งสองไฟล์

## 5. `lastSensingOkAt` — กลับทิศอคติของการ poll

> **สถานะ: รูปแบบตัดสินแล้ว (หัวข้อ 6) · ยังไม่ implement** · หัวข้อนี้เป็นเอกสารล้วน
> ยังไม่มีการแก้โค้ด และยังไม่ได้สร้าง vector เพิ่มเข้า
> `spec/visit_filter/vectors.json`
>
> ตัวเลข "ก่อน" ทั้งหมดข้างล่าง **วัดจากการรัน reducer ตัวปัจจุบันจริง** ส่วนตัวเลข
> "หลัง" วัดจากการ **จำลองข้อเสนอ** ด้วยการป้อน `SensingLost` ที่เวลาที่กติกาใหม่จะ
> คำนวณได้ — ซึ่งสมมูลกันโดยนิยาม (ดูหัวข้อ 5.2)

### 5.1 ปัญหาที่จะแก้

หัวข้อ 2 สรุปว่าฝั่ง Android **ไม่มีทางรู้เวลาที่เริ่มตาบอด** รู้ได้แค่ "ตอนที่ตื่นมา
ตาบอดอยู่" และคาบที่เราถูกปลุกกว้างระดับ **10–15 นาที** (ADR-15)

ให้ `T₀` = เวลาที่เริ่มตาบอดจริง (ไม่มีทางรู้) · `T₁` = เวลาที่เราตื่นมาเห็น ·
`L` = เวลาของ observation ล่าสุดที่เรายังยืนยันได้ว่ามองเห็นอยู่

```
   L  ────────  T₀  ────────  T₁
   │            │             │
   ยืนยันได้ว่า   เริ่มตาบอดจริง  เราเพิ่งรู้
   ยังมองเห็น    (ไม่มีทางรู้)    (ใช้อยู่ตอนนี้)
```

**เสมอ:** `L ≤ T₀ ≤ T₁`

ตอนนี้เราใช้ `T₁` ซึ่งเป็น**ขอบบน** → หักเวลาที่ตาบอดออกจากความเงียบ **น้อยกว่าความ
เป็นจริงเสมอ** → ความเงียบดูยาวเกินจริง → ปิดการมาเยือนเร็วเกินไป → **สร้าง visit
ปลอม ซึ่งคือบั๊กเดิมที่ `SensingLost` เกิดมาเพื่อแก้**

**ข้อเสนอ: ใช้ `L` ซึ่งเป็นขอบล่าง** → หัก **มากกว่า**ความเป็นจริงเสมอ → อคติกลับทิศ

### 5.2 กลไก — **ไม่ต้องเพิ่ม state ใหม่เลย**

ข้อสังเกตที่ทำให้ข้อเสนอนี้ถูกมาก: **ขณะที่ `sensing == available`
`state.lastObservationAtMs` คือ `L` อยู่แล้ว** ทุก observation ที่ถูกรับไว้ตอนที่ยัง
มองเห็นได้ ก็คือคำยืนยันว่าตอนนั้นเรามองเห็นได้

```
case SensingLost():
  if (sensing == available) {
    sensing       = lost
    sensingLostAtMs = (onset == observed)
        ? observation.atMs                          // รู้เวลาจริง — ใช้ค่าที่รายงานมา
        : (state.lastObservationAtMs ?? observation.atMs)   // poll เจอ — ใช้ขอบล่าง
  }
```

`SensingLost` ได้ฟิลด์ใหม่หนึ่งตัว คู่กับ `VisitStartEvidence` ที่มีอยู่แล้ว:

```dart
enum SensingLossOnset {
  /// รู้เวลาที่เริ่มจริง — delegate callback มาถึงขณะแอปยังมีชีวิต (เส้นทาง iOS)
  observed,
  /// poll ตอนถูกปลุกแล้วพบว่าตาบอด — รู้แค่ว่าเริ่มที่ไหนสักแห่งใน (L, T₁]
  boundedByLastKnownGood,
}
```

**ทำไมไม่ต้องมีฟิลด์ `lastSensingOkAtMs` แยก:** ตอนเปลี่ยนจาก `available` เป็น `lost`
observation ทุกตัวก่อนหน้าเกิดขึ้นตอนที่ยังมองเห็นได้ทั้งหมด `lastObservationAtMs`
จึงเท่ากับ `L` พอดี · ผลพลอยได้ที่สำคัญ: **การป้อน `SensingLost` ด้วยค่า `L` ไม่ถูก
ปฏิเสธจากด่านเวลาเดินถอยหลัง** เพราะ `L == lastObservationAtMs` เป๊ะ (เวลาเท่ากันรับได้)

⚠️ **ความถูกต้องขึ้นกับสัญญาข้อเดียวที่ต้องเขียนไว้ให้ชัด:**

> **ทุก observation ที่ป้อนเข้ามาขณะ `sensing == available` คือคำรับรองว่า ณ เวลานั้น
> ผู้เรียกตรวจแล้วและมองเห็นได้จริง**

ซึ่งตรงกับรูปแบบที่หัวข้อ 2 กำหนดไว้อยู่แล้ว (ตรวจสถานะก่อน แล้วค่อยป้อน observation
ของรอบนั้น) · ถ้าวันหนึ่งมีผู้เรียกที่ทำตามสัญญานี้ไม่ได้ ค่อยเพิ่มฟิลด์แยกทีหลัง —
**ตอนนี้ยังไม่คุ้ม เพราะกำลังจะเขียนตรรกะเดียวกันซ้ำอีกสองภาษา ทุกฟิลด์ที่เพิ่มคือ
ผิวสัมผัสที่ต้องพอร์ตสามที่**

### 5.3 พิสูจน์ว่าอคติเอนไปทาง "พลาด visit จริง"

ให้ `a` = `absentSinceMs` · `R` = เวลาที่กลับมามองเห็น · เวลาที่ถูกหัก (credit) คือ
`R − max(onset, a)` และ **ความเงียบที่มีผล** = ความเงียบจริง − credit

เพราะ `L ≤ T₀ ≤ T₁` และ `max(·, a)` เป็นฟังก์ชันไม่ลด:

```
R − max(T₁, a)   ≤   R − max(T₀, a)   ≤   R − max(L, a)
   หักน้อยกว่าจริง        ค่าที่ถูกต้อง         หักมากกว่าจริง
   (ใช้อยู่ตอนนี้)                            (ข้อเสนอ)
```

**เล็มมา (ทิศทางเดียว) — มีเงื่อนไข ห้ามอ้างลอย ๆ:**

> สำหรับลำดับ observation ที่ตายตัว **และตราบใดที่ช่วงตาบอดที่วัดได้ยังไม่ถึง
> `blindnessCeiling`** จำนวน `VisitStarted` **ไม่เพิ่มขึ้น**เมื่อ credit เพิ่มขึ้น

เพราะภายใต้เงื่อนไขนั้น `VisitStarted` ถูกยิงเฉพาะตอนที่ `RegionSeen` มาถึงขณะ
`visit == null` และ credit ที่มากขึ้นทำได้อย่างเดียวคือ **เลื่อนหรือยกเลิก**การปิด
การมาเยือน จึงมีจังหวะที่ `visit == null` น้อยลงหรือเท่าเดิม

**🛑 `blindnessCeiling` คือพจน์เดียวในระบบที่ทำลาย monotonicity นี้ — และมันทำลายจริง
ไม่ใช่ในทางทฤษฎี**

เพดานวัดจาก `sensingLostAtMs` ตัวเดียวกับที่ credit ใช้ · การเลื่อน `onset` ให้เร็ว
ขึ้นจึงทำสองอย่างพร้อมกันและ **ไปคนละทาง**:

| ผลของการเลื่อน `onset` ให้เร็วขึ้น | ทิศ |
|---|---|
| credit มากขึ้น → การมาเยือนเปิดค้างนานขึ้น | `VisitStarted` **ลดลง** |
| ช่วงตาบอดที่วัดได้ยาวขึ้น → ชนเพดานเร็วขึ้น → **ล้าง state ทิ้ง** | `VisitStarted` **เพิ่มขึ้น** |

เพดานแปลง "เครดิตมากขึ้น" ให้กลายเป็น "ล้าง state" ซึ่งเป็นการกระทำที่ **เพิ่ม**
จังหวะที่ `visit == null` — ตรงข้ามกับทุกอย่างที่ credit ทำ · ข้อสมมติของเล็มมาจึง
พังทันทีที่ข้ามเพดาน

**ตัวอย่างค้านอยู่ในเอกสารฉบับนี้เอง — ไม่ใช่กรณีสมมติ:** หัวข้อ 5.4 วัดได้ว่า
เลื่อน `onset` จาก 14 นาทีมาเป็น 0 แล้ว `VisitStarted` **เพิ่มจาก 1 เป็น 2**
· **ห้ามอ้างเล็มมานี้กับกรณีที่ช่วงตาบอดข้ามเพดาน**

*(หลักฐานเชิงประจักษ์ของทิศทางในกรณีที่ไม่มีเพดานมาเกี่ยว มีอยู่แล้วในตาราง
`cooldown_sweep`: cooldown 30 วินาที → 40 visit · 5 นาที → 1 visit บนไฟล์ iOS
ไฟล์เดียวกัน — ที่นั่นไม่มีการล้าง state เข้ามาเกี่ยวเลย)*

**ผลที่ตามมา:**

| | หักน้อยกว่าจริง (ตอนนี้) | หักมากกว่าจริง (ข้อเสนอ) |
|---|---|---|
| ความเงียบที่มีผล | ยาวเกินจริง | สั้นกว่าจริง |
| การมาเยือน | ปิดเร็วเกินไป | เปิดค้างนานเกินไป |
| `VisitStarted` | **มากเกินจริง** | **น้อยกว่าจริง** |
| อาการ | **visit ปลอม** — ลูกค้าที่ไม่ได้ไปไหนได้แจ้งเตือนซ้ำ | **พลาด visit จริง** — ลูกค้าที่ออกไปแล้วกลับมาถูกนับเป็นครั้งเดิม ไม่ได้แจ้งเตือน |

⚠️ **ตารางนี้ใช้ได้เฉพาะใต้เพดาน** ตามเงื่อนไขของเล็มมาข้างบน

**วัดจริงกับ reducer ตัวปัจจุบัน** (cooldown 5 น · เพดาน 15 น · เห็น@0 ·
ไม่เห็น@1น · ตาบอดจริงราว 2 น · นาฬิกาปลุกดังตอน 9 น · กลับมาเห็น@12น · เห็น@12น):

| | `SensingLost` ที่ | `VisitStarted` |
|---|---|---|
| ตอนนี้ (`T₁`) | 9 น | **2** ← visit ปลอม |
| ข้อเสนอ (`L`) | 1 น | **1** ✅ |

### 5.4 ⚠️ อคติกลับทิศ**เฉพาะใต้เพดาน** — เหนือเพดานมันพลิก

เพดานวัดจาก `sensingLostAtMs` ด้วย · ใช้ `L` แทน `T₁` ทำให้ช่วงตาบอด **ยาวขึ้นใน
สายตาของ reducer** จึงชนเพดานเร็วขึ้น และการชนเพดานคือการ **ล้าง state ทิ้ง** ซึ่ง
ทำให้ครั้งหน้าที่เห็นเป็น `VisitStarted` ใหม่

วัดจริง (อยู่ในโซนเงียบ ๆ ไม่มี observation เลย 14 นาที · poll เจอตอน 14 น ·
กลับมาเห็น@16น · เห็น@17น):

| | `SensingLost` ที่ | `VisitStarted` | เหตุผลที่ปิด |
|---|---|---|---|
| ตอนนี้ (`T₁`) | 14 น | **1** | — |
| ข้อเสนอ (`L`) | 0 น | **2** | `sensingLostBeyondCeiling` |

**นี่ไม่ใช่บั๊กของข้อเสนอ แต่ต้องเขียนไว้ให้ชัด:** `L = 0` แปลว่า **14 นาทีที่ผ่านมา
ไม่มี observation เลยสักตัวทั้งที่ควรจะอยู่ในโซน** ซึ่งตัวมันเองก็เป็นหลักฐานว่าเรา
น่าจะตาบอดมาเกือบทั้งช่วง · การประกาศว่า "ไม่รู้แล้ว ล้างทิ้ง" จึงตรงกับความจริง
มากกว่าการอ้างว่าการมาเยือนต่อเนื่อง · และ `VisitStarted` ตัวที่สองมี
`evidence = alreadyInsideAtFirstObservation` ซึ่ง **ชั้นแจ้งเตือนใช้กรองได้**
ถ้าไม่อยากยิงโปรโมชันซ้ำ

**ข้อสรุปที่ใช้ตั้งค่าได้จริง:**

> **`blindnessCeiling` ต้องสูงกว่าคาบที่เราถูกปลุกอย่างมีนัยสำคัญ** มิฉะนั้นขอบล่าง
> `L` จะลากช่วงตาบอดข้ามเพดานเป็นประจำ · ADR-15 วัดคาบที่ `AlarmManager` ส่งจริงได้
> ว่าเกาะกลุ่มที่ **10 นาที ×21 และ 15 นาที ×11** — **ค่า 15 นาทีที่ใช้ในเทสต์ตอนนี้
> จึงแคบเกินไปสำหรับกติกาใหม่** และนี่คือเหตุผลเพิ่มอีกข้อว่าทำไม `blindnessCeiling`
> ถึงต้องไม่มี default

### 5.5 กติกา `L` **มีเงื่อนไข ไม่ใช่กติกาเหมารวม**

> **`L` คือค่าที่ใช้เมื่อ *ไม่รู้* จุดเริ่มตาบอดเท่านั้น**
> ถ้ารู้จุดเริ่มจริง ต้องใช้ค่าที่รายงานมา — **ห้ามถอยไปใช้ `L`**

`L` ไม่ใช่ "ค่าที่ปลอดภัยกว่า" ที่จะเอาไปใช้ทุกที่ · มันคือ **ขอบล่างของช่วงความไม่รู้**
การเอาไปใช้ตอนที่เราไม่ได้ไม่รู้ คือการสร้างความไม่รู้ขึ้นมาเองแล้วหักเวลาที่ไม่เคย
ตาบอดจริงทิ้งไปด้วย

| ผู้เรียกรู้อะไร | `onset` ที่รายงาน | `sensingLostAtMs` ที่ reducer ใช้ |
|---|---|---|
| **รู้จุดเริ่มจริง** — delegate callback มาถึงขณะแอปมีชีวิต (เส้นทาง iOS) | `observed` | `observation.atMs` **ตามที่รายงานมา** |
| **ไม่รู้** — poll ตอนถูกปลุกแล้วพบว่าตาบอด (เส้นทาง Android ทั้งหมด) | `boundedByLastKnownGood` | `lastObservationAtMs` = `L` |

ผู้เรียกรายงานแค่ **"รู้จุดเริ่มหรือไม่"** ไม่ได้เลือกว่าจะให้หักเท่าไร — การตัดสินว่า
เครดิตถึงไหนอยู่ที่ reducer ที่เดียว

#### ผลวัดจริงที่พิสูจน์ว่าใช้เหมารวมแล้วพลาด visit จริง

สถานการณ์: เห็น@0 · ไม่เห็น@1น · มี observation@2น · **ตาบอดจริงตอน 9 น และเรารู้แน่**
· กลับมามองเห็น@12น · เห็น@12น

**ความจริงภาคสนามคือลูกค้าออกไป 8 นาทีแล้วกลับมา = 2 การมาเยือน** (ช่วง 1น→9น เป็น
ความเงียบจริงที่เกิน cooldown 5 นาที ไม่เกี่ยวกับการตาบอดเลย)

| `onset` ที่ใช้ | `SensingLost` ที่ | credit | `VisitStarted` | |
|---|---|---|---|---|
| `observed` (ถูกต้อง) | 9 น | 3 น | **2** | ✅ ตรงความจริงภาคสนาม |
| เหมารวมใช้ `L` | 2 น | 10 น | **1** | ❌ **พลาด visit จริงไป 1 ครั้ง** |

การเหมารวมกลืนความเงียบจริง 8 นาทีเข้าไปเป็น "ช่วงที่เราตาบอด" ทั้งที่ 7 นาทีแรก
ของมันเรามองเห็นได้ปกติ — ลูกค้าที่เดินออกไปจริงแล้วกลับเข้ามาใหม่จึงถูกนับเป็น
การมาเยือนครั้งเดิม และไม่ได้รับแจ้งเตือน

นี่คือหน้าตาของความล้มเหลวฝั่ง "พลาด visit จริง" แบบเป็นรูปธรรม — **ยอมรับได้เมื่อ
เป็นราคาของความไม่รู้ ยอมรับไม่ได้เมื่อเรารู้อยู่แล้ว**

| `sensing-onset-bound-crosses-ceiling` | หัวข้อ 5.4 — อคติพลิกเหนือเพดาน · **เพดานแคบ** | `VisitStarted` **2** · ตัวแรกปิดด้วย `sensingLostBeyondCeiling` |
| `sensing-onset-bound-under-wide-ceiling` | ลำดับ observation **ชุดเดียวกันเป๊ะ** แต่ **เพดานกว้าง** | `VisitStarted` **1** — พิสูจน์ว่าเพดานคือตัวแปรที่พลิกผล ไม่ใช่ลำดับ observation |
| `observations-while-blind-do-not-move-onset` | observation ที่มาระหว่างตาบอดต้องไม่เลื่อน `sensingLostAtMs` ที่ล็อกไว้แล้ว | ช่วงตาบอดยังวัดจาก `L` เดิม |
| `sensing-lost-with-no-prior-observation` | process เกิดมาตาบอดเลย ไม่มี `L` | fallback ไป `atMs` · **อคติเดิมยังเหลืออยู่ในเคสนี้** |

สองเคสกลางต้อง **ใช้ลำดับ observation เดียวกันและต่างกันแค่ `blindnessCeilingMs`**
ตามคำตัดสินข้อ 2 ข้างล่าง — คนอ่านไฟล์ vector ต้องเห็นได้จากไฟล์เดียวว่าเพดานทำอะไร
โดยไม่ต้องไปเปิดโค้ด

เคสสุดท้ายคือรูที่ปิดไม่ได้จากใน reducer — **ผู้เรียกต้องเก็บ `lastObservationAtMs`
ลงดิสก์พร้อม state ที่เหลือ** ไม่งั้นทุกครั้งที่ process เกิดใหม่จะเสีย `L` ไป และ
กลับไปมีอคติแบบเดิม (`PORTING.md` ข้อ 7: ต้องใช้ `commit()` ไม่ใช่ `apply()`)

## 6. คำตัดสิน (2 ก.ย. 2026) — ยังไม่ลงมือเขียนโค้ด

### 6.1 กติกา `L` อยู่ใน reducer **ไม่ใช่ฝั่งผู้เรียก**

หัวข้อ 5.2 ตั้งข้อสังเกตว่ากติกาใหม่สมมูลกับ "ผู้เรียกป้อน `SensingLost` ด้วย
`atMs = lastObservationAtMs`" จึงทำได้โดยไม่ต้องแตะ reducer — **ทางลัดนั้นถูกปฏิเสธ**

**เหตุผล:** ข้ออ้างเดียวของทางลัดคือ "ได้ทดลองบนเครื่องจริงเร็วขึ้น" ซึ่งไม่จริง —
**บนเครื่องยังไม่มี reducer อยู่เลย** ต้องพอร์ตเป็น Kotlin ก่อนถึงจะทดลองอะไรได้
ทางลัดจึงไม่ได้ประหยัดขั้นตอนใด แลกมาแค่การย้ายกติกาไปอยู่**นอกสายตาของไฟล์ vector**
ซึ่งเป็นสิ่งเดียวที่จับได้เมื่อสามภาษาเพี้ยนจากกัน

**รูปแบบที่ตัดสินแล้ว:**

```dart
enum SensingLossOnset { observed, boundedByLastKnownGood }
```

**ผู้เรียกรายงานแค่ว่า "รู้จุดเริ่มตาบอดหรือไม่" · reducer เป็นคนตัดสินว่าเครดิตถึงไหน**
— ผู้เรียกไม่มีสิทธิ์เลือกเวลาที่จะให้หัก การแบ่งหน้าที่แบบนี้ทำให้กติกาทั้งหมดอยู่ใน
ไฟล์ vector และผู้เรียกทั้งสามภาษาผิดพลาดได้แค่ทางเดียวคือรายงาน `onset` ผิด ซึ่งเป็น
ข้อเท็จจริงที่ผู้เรียกรู้ดีที่สุดอยู่แล้ว

### 6.2 `blindnessCeiling` เป็น **required parameter ไม่มี default**

ยืนยันของเดิมและเพิ่มเหตุผลข้อที่ทำให้ห้ามผ่อน:

**ห้ามใส่ default แล้วเปลี่ยนทีหลังแบบเงียบ ๆ** — ตอนนี้มีเทสต์ **73 ตัว** ที่จะ
**สืบทอดค่าใหม่ทันทีโดยไม่มี commit ไหนบอกว่าค่าเปลี่ยน** · การเปลี่ยนพฤติกรรมของทั้ง
ชุดเทสต์ต้องอ่านออกจาก diff เสมอ

**ผลกับไฟล์ vector:** ทุกเคส **ต้องระบุ `blindnessCeilingMs` ในตัวเคสเอง** (ทำแล้ว
ตั้งแต่รอบที่แล้ว) และต้องมี **ทั้งเคสเพดานแคบที่ชนเพดาน และเคสเพดานกว้างที่ไม่ชน**
บนลำดับ observation ชุดเดียวกัน — **สัญญาต้องอ่านออกจากไฟล์เดียว** ไม่ต้องเปิดโค้ด
ประกอบ

### 6.3 ค่าเพดานที่จะใช้จริง — **ยังไม่ตัดสิน**

**สิ่งที่รู้แน่แล้ว:** **15 นาทีแคบเกินไป** · ADR-15 วัดคาบที่ `AlarmManager` ส่งจริง
ได้ว่าเกาะกลุ่มที่ **10 นาที ×21 และ 15 นาที ×11** — เพดานที่เท่ากับคาบปลุกแปลว่า
**ชนเพดานเป็นกิจวัตร** ไม่ใช่กรณียกเว้น และเมื่อรวมกับกติกา `L` ที่ลากช่วงตาบอดให้
ยาวขึ้น จะยิ่งชนถี่ขึ้นไปอีก (หัวข้อ 5.4)

**สิ่งที่ยังไม่รู้และเป็นตัวกำหนดค่าจริง:** **ลูกค้าอยู่ในสาขานานเท่าไร** — เป็นข้อมูล
ฝั่งธุรกิจ ไม่ใช่ข้อมูลที่วัดได้จาก log สองคืนที่มี (สองคืนนั้นคือมือถือวางนิ่งข้าง
beacon ทั้งคืน ไม่ใช่พฤติกรรมลูกค้า)

🛑 **ห้ามใส่ตัวเลขลงโค้ดโดยอ้างว่า "น่าจะพอ"** — ค่าที่เดามาจะกลายเป็นค่าที่ไม่มีใคร
กล้าแก้ภายในสามเดือน และจะถูกอ้างต่อว่า "ค่าที่ใช้อยู่" เหมือนที่เกิดกับ
`exitTimeoutSeconds` มาแล้ว (ADR-15)
