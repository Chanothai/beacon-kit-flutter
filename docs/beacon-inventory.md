## 🔎 ข้อสังเกตเชิงฮาร์ดแวร์ — ความถี่ที่เห็นต่างกันมากระหว่าง #2/#3 (เพิ่ม 14 ก.ย. 2026)

**จากไฟล์เดียวกัน** (`docs/test-data/2026-09-14_android_overnight_proximity_redmi.log`, นับเฉพาะบรรทัด
2207 เป็นต้นไป — ดูรายละเอียดที่ `test-checklists/android_background_scanning.md`):

| | **#2** (`9902/2`, MAC `55:50`) | **#3** (`9903/3`, MAC `55:4D`) |
|---|---|---|
| จำนวนบรรทัด `event=proximity` | **197** | **1157** |
| `rssi` มัธยฐาน | **−52 dBm** | **−41 dBm** (แรงกว่า/ใกล้กว่า) |
| `reason=stale` | **0 ครั้ง** | **464 ครั้ง (40%)** |
| ช่วงห่างสูงสุดระหว่างบรรทัดที่เห็น (ไม่ใช่ความเงียบจริง — ดูเหตุผลใน ARCHITECTURE.md ADR-20 หัวข้อ 7) | **21.0 ชั่วโมง** (13 ก.ย. 09:54 → 14 ก.ย. 06:54) โดยไม่มี `stale` เลยสักครั้งในช่วงนั้น | สูงสุด ~2 ชั่วโมงต่อครั้งของความเงียบจริงที่วัดได้ (ก่อน/หลัง `stale`) |

**ห้ามสรุปว่า #2 แบตหมด/ฮาร์ดแวร์เสีย** — ตัวเลขข้างบนเป็น**ข้อสังเกต**เท่านั้น มีคำอธิบายอื่นที่เข้ากับ
ข้อมูลได้พอ ๆ กันหรือมากกว่า:

1. **#2 อาจแค่นิ่งอยู่ bucket เดิมนาน** — ช่วงห่าง 21 ชม. ที่ไม่มี `stale` แม้แต่ครั้งเดียวพิสูจน์ว่า raw
   sample ยังมาต่อเนื่อง (ไม่งั้นต้อง stale ภายใน 60 วินาทีแรกของความเงียบจริงตาม `staleAfterMillis`
   ที่ใช้งานจริงในบิลด์นี้) เพียงแค่ไม่เปลี่ยน bucket เลยจึงไม่มีบรรทัดถูกพิมพ์ — ตรงกับพฤติกรรมของ
   #2 ที่ไม่เคย flap เหมือน #3 (ดู ARCHITECTURE.md ADR-20 หัวข้อ 7 สำหรับคำอธิบายเต็มว่าทำไม "ช่วงห่าง
   ระหว่างบรรทัด log" ไม่เท่ากับ "ช่วงความเงียบจริง")
2. **#3 อาจกำลัง flap ที่ขอบ `immediate`/`near`** — หนี้เดิมที่ ADR-19 หัวข้อ 7 บันทึกไว้แล้วว่าขอบนี้
   ไม่มี hysteresis รอบนี้นับจำนวน flap ได้จริง 212 รอบ (`near`→`immediate`→`near`) ซึ่งอธิบาย
   จำนวนบรรทัดที่สูงกว่ามากของ #3 ได้บางส่วนโดยไม่ต้องอ้างเรื่องแบต/ฮาร์ดแวร์เลย
3. **463 จาก 464 ครั้งที่ #3 หลุด `stale` เกิดตอน `standbyBucket=workingSet`** (ไม่ใช่ `rare`/`active`)
   — สอดคล้องกับสมมติฐาน "MIUI/App Standby หน่วงรอบสแกนตอนแอปอยู่เบื้องหลังนานพอสมควร" มากกว่า
   "บีคอนตายเป็นช่วง ๆ" แต่**ยังพิสูจน์เป็น causation ไม่ได้จากข้อมูลนี้อย่างเดียว**

**สิ่งที่ต้องตรวจเพื่อยืนยัน/ปฏิเสธแต่ละสมมติฐาน (ยังไม่ได้ทำ):**

- เปิดแอป **KBeacon** ตรวจ **แรงดันแบตเตอรี่จริง** ของ #2 กับ #3 เทียบกัน (ถ้า #2 โวลต์ต่ำกว่าชัดเจน
  สนับสนุนสมมติฐานแบตอ่อน — แต่รุ่นนี้ไม่ได้บอกว่ารายงาน % แบตแม่นแค่ไหน ต้องเทียบเป็นโวลต์ดิบ)
- ตรวจตำแหน่งจริงของ #2 ว่ายังอยู่ตำแหน่งเดิมตลอด 2 วันหรือถูกใครขยับ (เทียบกับกฎในไฟล์นี้ที่บังคับ
  บันทึกความเคลื่อนไหวของบีคอนทุกครั้ง — ถ้าไม่มีบันทึกว่าย้าย แปลว่าตามทฤษฎีไม่ควรขยับ แต่ต้องเช็ค
  ด้วยตาจริงเพราะเคยพลาดมาแล้วกับเคส `bigc-test` เงียบ/กลับมาก่อนหน้านี้)
- นับจำนวน raw `ScanResult` ต่อ MAC จาก logcat ดิบ (ไม่ใช่จากไฟล์หลักฐานที่กรองเฉพาะ transition แล้ว)
  ในช่วงเวลาสั้น ๆ ที่ควบคุมได้ เพื่อวัด "อัตราสัญญาณจริง" ของ #2 แยกจาก "อัตราการเปลี่ยน bucket" —
  เป็นวิธีเดียวที่จะตอบคำถามข้อ 1 ข้างบนได้ตรง ๆ แทนการอนุมานจากความเงียบของไฟล์หลักฐาน
- ตรวจระยะทางจริงจากจุดวางเครื่องทดสอบไปยัง #2 กับ #3 ว่าต่างกันแค่ไหน — คำอธิบายที่ง่ายที่สุดและ
  ยังไม่ถูกตัดออกเลยคือ **#2 อยู่ไกลกว่า #3 จริง ๆ** (สอดคล้องกับ rssi มัธยฐานที่อ่อนกว่า −52 vs −41)
  ไม่ใช่เรื่องแบตหรือฮาร์ดแวร์เลย — ต้องวัดระยะจริงก่อนจะไปตั้งสมมติฐานที่ซับซ้อนกว่านั้น

## ⚠️ ความเสี่ยงที่ยอมรับไว้ — password ค่าโรงงาน

**#2 และ #3 ยังใช้ password ค่าโรงงาน** — ใครก็ตามที่อยู่ในระยะ BLE และรู้ค่า default
ของรุ่นนี้ **เขียนทับ UUID / major / minor / TX power ได้ทั้งหมด**

- **ยอมรับได้เฉพาะระดับ POC ในออฟฟิศ** ที่ทุกตัวอยู่ในสายตาและไม่มีข้อมูลลูกค้าเกี่ยวข้อง
- 🔴 **ห้ามนำสภาพนี้ขึ้น pilot หรือสาขาจริงเด็ดขาด** — ต้องเปลี่ยน password ทุกตัว
  และบันทึกในตารางข้างบนก่อน

## หนี้ที่ผูกกับไฟล์นี้

1. ~~แมป tag → `major/minor` ให้ได้~~ **ปิดแล้ว 14 ก.ย. 2026** — ADR-20 หัวข้อ 1 (แก้ 11 ก.ย. 2026)
   เปลี่ยนให้ Android ถอด major/minor จากเฟรมโดยตรงแทนการอ่านจาก region spec แล้ว รอบเดินจริง
   12-14 ก.ย. 2026 (`docs/test-data/2026-09-14_android_overnight_proximity_redmi.log`, นับจากบรรทัด
   2207) ยืนยันว่า `beacon=` มีค่าจริงทุกบรรทัด (ไม่มี `n/a` เลย) — แมปได้ตรง ๆ จากการเห็น `beacon=`
   กับ `mac=` ในบรรทัดเดียวกัน: **`beacon=9902/2` คู่กับ `mac=55:50` เสมอ** และ **`beacon=9903/3` คู่กับ
   `mac=55:4D` เสมอ** (ยืนยันด้วย `grep -oE 'beacon=[^ ]+ mac=[^ ]+' | sort | uniq -c` → มีแค่ 3 คู่ค่า
   ที่เป็นไปได้: `beacon=9902/2 mac=55:50` (197 บรรทัด), `beacon=9903/3 mac=55:4D` (693 บรรทัด), และ
   `beacon=9903/3 mac=n/a` (464 บรรทัด — เฉพาะบรรทัด `reason=stale` ที่ไม่มี `ScanResult` สดคู่มาด้วยตาม
   ADR-20 หัวข้อ 3 ไม่ใช่ค่าที่ขัดแย้งกัน) **ไม่มีคู่ที่ผิด เช่น `beacon=9902/2 mac=55:4D` เลยสักบรรทัด**
   — ผลใส่ไว้ในตารางบีคอนด้านบนแล้ว
2. **calibration ขั้น 1** — วัดว่า `txPower = −51 dBm` ตรงกับ RSSI จริงที่ 1 เมตรไหม
   แล้วบันทึกส่วนต่างต่อบีคอนต่อสถานที่ลงตารางข้างบน
   (โปรโตคอลอยู่ที่ `test-checklists/android_background_scanning.md`)
3. **เปลี่ยน password ทุกตัวก่อน pilot** และบันทึกในตาราง
4. **เติมค่าของ #1** เมื่อได้ตัวเครื่องกลับมา
5. **ยืนยันสาเหตุที่ #2/#3 มีความถี่ที่เห็นต่างกันมาก** — ดูหัวข้อ "🔎 ข้อสังเกตเชิงฮาร์ดแวร์" ด้านบน
   (เพิ่ม 14 ก.ย. 2026) ยังไม่มีข้อสรุป มีแค่สมมติฐานที่ต้องตรวจเพิ่ม
