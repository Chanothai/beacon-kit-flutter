# ความจริงภาคสนามของแต่ละไฟล์ — เกณฑ์รับของชั้นกรองกลาง

ไฟล์นี้บันทึก **สิ่งที่เกิดขึ้นจริงในโลก** ระหว่างที่แต่ละ log ถูกเก็บ แยกจาก
**สิ่งที่ระบบรายงาน** โดยเด็ดขาด

## ทำไมต้องมีไฟล์นี้แยกจาก README

`README.md` อธิบายว่าไฟล์ไหนคืออะไร · ไฟล์นี้ตอบคนละคำถาม: **"คำตอบที่ถูกต้อง
คืออะไร"** — ซึ่งเป็นสิ่งที่ log บอกไม่ได้ เพราะ log คือสิ่งที่เราอยากตรวจสอบ

สอง log ในโฟลเดอร์นี้เก็บภายใต้เงื่อนไขที่ **คำตอบถูกต้องรู้ล่วงหน้าแน่นอน**
จึงใช้เป็น **เกณฑ์รับ (acceptance criteria) ของชั้นกรองกลาง** ได้ตรง ๆ:
ตัวกรองที่อ่านสองไฟล์นี้แล้วไม่ได้ผลตามตารางข้างล่าง คือตัวกรองที่ยังไม่ผ่าน

⚠️ **ห้ามแก้ไฟล์ `.log` ทั้งสองไฟล์ไม่ว่ากรณีใด** แม้แต่การจัดรูปแบบใหม่ให้เข้ากับ
รูปแบบ log ปัจจุบัน — มันคือหลักฐานดิบของสิ่งที่เกิดขึ้นจริง การแก้ย้อนหลังทำให้
มันเชื่อถือไม่ได้ทันที · ตัวอ่านทุกตัวต้องรองรับรูปแบบเก่าแทน

## เงื่อนไขการทดสอบ (เหมือนกันทั้งสองคืน)

- มือถือ **วางนิ่ง** จอดับ ล็อกเครื่อง แอปอยู่เบื้องหลัง
- beacon **K9P ตัวเดียว วางนิ่งข้าง ๆ** ไม่ถอดแบต ไม่ขยับ
- **ไม่มีใครแตะอะไรเลยทั้งคืน**

### ⇒ ความจริงภาคสนาม

> **`enter` 1 ครั้ง ตอนเริ่ม · `exit` 0 ครั้ง ตลอดทั้งคืน**

ทุก `exit` ในสองไฟล์นี้คือ **exit ปลอม** ทุกบรรทัดโดยไม่มีข้อยกเว้น

| | `2026-08-30_overnight_region_flapping.log` | `2026-09-01_android_overnight_region_flapping.log` |
|---|---|---|
| แพลตฟอร์ม | **iOS** (CoreLocation region monitoring) | **Android** (`startScan` + `PendingIntent` + นาฬิกาปลุก) |
| ช่วงเวลา | 2026-08-30 18:34 → 08-31 08:41 (14 ชม 6 น) | 2026-09-01 14:14 → 09-02 08:48 (18 ชม 33 น) |
| รูปแบบบรรทัด | **5 คอลัมน์** (ก่อนมี `processId`) | **6 คอลัมน์** + ตัวระบุ process ครบชุด |
| `enter` ดิบ | 86 | 63 |
| `exit` ดิบ | 86 | 62 |
| `launch` | 4 | 94 |
| **enter+exit ดิบ** | **172** | **125** |
| **ความจริงภาคสนาม** | **enter 1 · exit 0** | **enter 1 · exit 0** |
| **exit ปลอม** | **86** | **62** |

### ผลที่ตัวกรองต้องให้ได้

ใช้กติกา **รวมคู่ที่ห่างกัน < 5 นาที แล้วนับเฉพาะช่วงที่อยู่นานเกิน 2 นาที**
(กติกาที่ได้จากการวิเคราะห์ log iOS คืน 30 ส.ค.):

| | iOS 30 ส.ค. | Android 1 ก.ย. |
|---|---|---|
| ช่วง "อยู่ในโซน" ดิบ | 86 | 63 |
| หลังรวมคู่ที่ห่าง < 5 นาที | **1** | **1** |
| หลังตัดช่วงสั้นกว่า 2 นาที | **1** | **1** |
| ช่วงเดียวที่เหลือ | 08-30 18:34:47 → 08-31 08:41:07 (14.11 ชม) | 09-01 15:50:11 → 09-02 08:48:34 (16.97 ชม) |
| **→ ตรงกับความจริงภาคสนาม** | ✅ | ✅ |

**ช่วงสุดท้ายของทั้งสองไฟล์เปิดค้าง** (ไฟล์จบขณะยังอยู่ในโซน) ตัวกรองต้องปิดช่วง
ที่ขอบข้อมูล ไม่ใช่ทิ้งช่วงนั้น — ถ้าทิ้ง จะได้ 0 ช่วงซึ่งผิดจากความจริง

```bash
dart run tool/analyze_region_log.dart docs/test-data/<ไฟล์>.log
```

## สิ่งที่สองไฟล์นี้ **พิสูจน์ไม่ได้** — ต้องระบุทุกครั้งที่อ้างถึง

- **คาบการส่งผลสแกนจริง** — log บันทึกเฉพาะตอน**สถานะเปลี่ยน** ผลสแกนที่เข้ามา
  ระหว่างที่ยังอยู่ในโซนไม่ทิ้งร่องรอยเลย ตัวเลข "ช่องว่างของผลสแกน" ที่คำนวณได้
  จากไฟล์นี้เป็น **ขอบล่างเท่านั้น** (`exitTimeoutSeconds` + ช่วง exit→enter)
- **เวลาจริงตั้งแต่เห็น beacon ครั้งสุดท้ายจนถึงตอนที่ประกาศ exit** — ต้องใช้ฟิลด์
  `sinceLastSeenMs` / `scheduledAtElapsed` / `firedAtElapsed` ซึ่ง **ยังไม่มีใน
  บิลด์ที่เก็บสองไฟล์นี้** (ตรวจได้: `grep -c sinceLastSeenMs` → 0 ทั้งสองไฟล์)
- **สาเหตุของ exit ปลอม** — ไฟล์บอกได้ว่า *เกิดเมื่อไร* และ *มีรูปแบบอย่างไร*
  แต่ไม่ได้บอก *ทำไม* การอ้างสาเหตุต้องมีเอกสารแพลตฟอร์มกำกับ
  (`docs/sources/android_background_ble.md`)

## รูปแบบเวลาที่ต้องระวัง

ทั้งสองไฟล์ใช้ **เวลาท้องถิ่นของเครื่องทดสอบ + offset (`+07:00`)** ไม่ใช่ UTC —
ตัวกรองที่แปลงเป็น UTC แล้วรายงานชั่วโมงจะได้กราฟ "flap ต่อชั่วโมง" ที่เลื่อนไป
7 ชั่วโมง ซึ่งทำให้ข้อสรุปเรื่อง "ช่วงกลางคืน" ผิดทั้งหมด
