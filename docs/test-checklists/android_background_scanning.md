### ⚠️ บิลด์ถัดไปจะรีเซ็ต proximity state ทั้งหมด — ตั้งใจ ไม่ใช่ regression (เพิ่ม 11 ก.ย. 2026)

รอบแก้ ADR-20 ที่เปลี่ยน gate key จาก `region|MAC` เป็น `region|uuid|major|minor` (ดู ARCHITECTURE.md
ADR-20 หัวข้อ 3 — ส่วน "Migration ของ state บนดิสก์") บังคับให้เปลี่ยน `KEY_STATES` เป็น `"states_v2"`
และ drop entry รูปแบบเก่าทิ้งทั้งหมดตอนอัปเกรด **เครื่องที่รันบิลด์เก่าค้างอยู่ (รวม Redmi Note 9 ที่จะ
ติดตั้งบิลด์ใหม่ในรอบทดสอบถัดไป) จะเห็น:**

- บรรทัดหลักฐาน `store=migrated_dropped=<n>` หนึ่งครั้งตอน `onReceive` แรกหลังอัปเกรด
  (ขีดล่าง ไม่ใช่เว้นวรรค — คอลัมน์ `store=` แทนที่ช่องว่างด้วย `_` อยู่แล้วตามกฎเดิมของ
  `rawSignalsSuffix` เพราะคอลัมน์สัญญาณดิบคั่นด้วยช่องว่าง)
- `from=none` สำหรับ**ทุกบีคอนที่เคยยืนยัน bucket ไว้** ในรอบ sighting แรกหลังอัปเกรด (dwell/window
  เริ่มนับใหม่จากศูนย์เพราะ key รูปแบบเก่าอ่านไม่ได้แล้วโดยตั้งใจ ไม่ใช่ถูก parse ผิดเงียบ ๆ)

**ห้ามตีความสองอาการนี้ว่าเป็น regression ของ ADR-14/ADR-17 (enter/exit)** — ชั้น 1 ไม่ถูกแตะเลยในรอบนี้
ผลกระทบจำกัดอยู่แค่ชั้น 2 (proximity) เท่านั้น และเป็นผลที่คาดไว้ล่วงหน้าตามกติกา migration ของ ADR-20

- เส้นทาง exit เฉพาะ region: `adb logcat | grep proximityGateStore.clearRegion` — ต้องเห็นบรรทัด
  รูปแบบ `proximityGateStore.clearRegion region=<id> removed=<n> source=<onExitAlarm|reconcile>`

  `.clear` และ `.clearRegion`) — ต้องเห็น `source=start` / `source=stop` / `source=restoreAfterBoot`

### 📐 โปรโตคอล calibration — ขั้นที่ 1 (ยังไม่ได้ทำ)

**เป้าหมาย:** ตอบว่าค่า `txPower` ที่อยู่ในเฟรมตรงกับ RSSI จริงที่ 1 เมตรไหม
**ก่อน**จะไป calibrate `n` — เพราะถ้าขั้นนี้เพี้ยน การ calibrate `n` จะไปดูดซับ
ความผิดพลาดเข้ามาไว้ใน `n` แล้วได้ค่าที่พอดีกับระยะที่ใช้ calibrate แต่ผิดที่ระยะอื่น

1. วางบีคอนและเครื่องห่างกัน **1.00 เมตร** เส้นตรง ไม่มีสิ่งกีดขวาง ความสูงเท่ากัน
2. เก็บ `rssi=` จากไฟล์หลักฐานอย่างน้อย **30 sample ต่อบีคอน** แล้วหา**มัธยฐาน**
   (ไม่ใช่ค่าเฉลี่ย — RSSI มี outlier เป็นปกติ)
3. **เทียบมัธยฐานกับ `txPower=` ที่อยู่ใน _บรรทัดเดียวกันของไฟล์หลักฐาน_
   — ไม่ใช่กับ measured power ที่แอป KBeacon แสดง**
   > 🔴 **ข้อนี้คือหัวใจของขั้นที่ 1** สองค่านั้นต่างกัน 8 dB โดยการออกแบบ
   > (แอปอ้างอิง 0 dBm ส่วนเฟรมรวมกำลังส่งจริงไว้แล้ว) · ถ้าเทียบกับค่าในแอป
   > จะสรุปว่า "เพี้ยน 8 dB" ทั้งที่ไม่มีอะไรเพี้ยนเลย — **ความผิดพลาดนี้เกิดขึ้น

   `docs/beacon-inventory.md`
5. **ถ้าส่วนต่างเกิน ±3 dB** ให้ถือว่าค่าในเฟรมใช้เป็น reference ไม่ได้ในสถานที่นั้น

## หมายเหตุถาวร — วิธีอ่าน `exitReason=staleReconcile` (ADR-17)

> ⚠️ **`timestampMillis` ของบรรทัดที่มี `exitReason=staleReconcile` คือเวลาที่
> `reconcile()` "ตรวจพบ" ว่าสถานะค้าง ไม่ใช่เวลาที่อุปกรณ์ออกนอกโซนจริง** — สอง
> เวลานี้ต่างกันได้มาก (ในเคสจริงที่เคยเจอคือหลายชั่วโมง เพราะนาฬิกาปลุกถูกระงับไว้
> ทั้งคืน) **ค่าที่บอกความจริงเรื่อง "หายไปนานแค่ไหน" คือ `sinceLastSeenMs` เท่านั้น**
> ห้ามใช้ `timestampMillis` ลบกับเวลาที่คาดว่าออกนอกโซนมาคำนวณ dwell/gap — ต้องอ่าน
> `sinceLastSeenMs` ตรง ๆ จากบรรทัดนั้นเสมอ (ดูรายละเอียดฟิลด์เต็มใน
> `android_background_runbook.md` §0.2 ตาราง "ฟิลด์ในคอลัมน์สัญญาณดิบ" แถว
> `exitReason`) — บันทึกไว้ในไฟล์นี้เพราะเป็นจุดที่คนอ่านผลทีหลังตีความผิดง่ายที่สุด
> ถ้าไม่มีบรรทัดนี้กำกับ

- **แถว 5 (§6):** ทำ §6.1 (บังคับ Doze ด้วย `adb`) และ §6.2 (แบบจริง — ถอด/ใส่แบต K9P พร้อมนาฬิกาแยก) ตามขั้นตอนเต็มรูปแบบ แล้ววัด `sinceLastSeenMs` เทียบกับเวลาที่นาฬิกาแยกจับได้จริง — ตัวเลขที่มีตอนนี้มาจากความเงียบตามธรรมชาติของการวางเครื่องนิ่งข้ามคืน ไม่ใช่การวัดที่ควบคุมจุดเริ่มต้น (K9P ออกนอกระยะเมื่อไร) ได้แม่นยำ

## บันทึกรอบทดสอบ

**หมายเหตุ:** ตอนนี้ติดตั้งลงเครื่องได้แล้ว (ตัวบล็อก `INSTALL_FAILED_USER_RESTRICTED`
เดิมหมดอายุไปแล้ว) และมีข้อมูลจริงจากเครื่องอยู่ในตารางผลด้านบนแล้ว (แถว 1 และ 5) —
แต่นั่นคือข้อมูลที่**เกิดขึ้นเองระหว่างเก็บ log ข้ามคืนของเคสอื่น** ไม่ใช่รอบทดสอบที่
ตั้งใจเดินตาม protocol ของแต่ละเคสตามรูปแบบด้านล่างนี้ — ยังไม่มีการบันทึกรอบทดสอบ
แบบตั้งใจตามรูปแบบนี้เลยสักรอบ

รูปแบบที่ต้องบันทึกต่อรอบ:

```
วันที่/เวลา · เคสข้อที่ · Autostart · battOpt · location_mode
processId ก่อน / processId หลัง
เวลาถอดแบต → เวลาได้ exit  = ...
เวลาใส่แบต  → เวลาได้ enter = ...
บรรทัด log ที่เป็นหลักฐาน (คัดลอกมาทั้งบรรทัด)
```
