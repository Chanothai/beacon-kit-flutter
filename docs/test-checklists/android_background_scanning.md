## สถานะรวม

**`code-complete, unverified`** — ตามนิยามใน CONTRIBUTING ข้อ 4:
โค้ดครบ คอมไพล์ผ่าน เทสต์เขียว **แต่ยังไม่เคยรันบนอุปกรณ์จริงเลยแม้แต่ครั้งเดียว**

### 🛑 ตัวบล็อกที่ทำให้ยังทดสอบไม่ได้

ติดตั้งแอปลงเครื่องไม่ได้ — MIUI ปฏิเสธ:

```
adb: failed to install app-debug.apk:
  Failure [INSTALL_FAILED_USER_RESTRICTED: Install canceled by user]
```

ไม่ใช่ปัญหาที่แก้จากฝั่งเครื่องพัฒนาได้ (`settings put` ถูกปฏิเสธด้วย
`SecurityException`) — **เจ้าของเครื่องต้องเปิด "ติดตั้งผ่าน USB" ใน MIUI
Developer options เอง** วิธีทำอยู่ใน runbook §0

## สิ่งที่ยืนยันแล้ว — และขอบเขตของมัน

รายการนี้ **ไม่ใช่หลักฐานว่าฟีเจอร์ทำงาน** ตาม CONTRIBUTING ข้อ 4:
"unit test ที่เขียวไม่นับเป็นการยืนยัน สำหรับอะไรก็ตามที่คุยกับ OS หรือฮาร์ดแวร์"

| สิ่งที่ยืนยันแล้ว | ยืนยันด้วยอะไร | **พิสูจน์อะไรไม่ได้** |
|---|---|---|
| ไบต์ของ `ScanFilter` เรียงตรงตามสเปก iBeacon (UUID / major / minor / mask) | `BeaconRegionSpecTest` (6 เทสต์ · JVM) | ว่าตัวกรองนี้จะ match beacon จริงบนอากาศ |
| รูปแบบบรรทัด log 6 คอลัมน์ตรงกันทั้งสองแพลตฟอร์ม | `BackgroundEvidenceLogTest` (Kotlin) + `testLogLineHasSixTabSeparatedColumnsInOrder` (Swift) + `evidence_log_line_test.dart` | ว่าไฟล์จะถูกเขียนได้จริงตอน process ถูกปลุก |
| ตัววิเคราะห์ยังอ่าน log รูปแบบเก่า 5 คอลัมน์ได้ | รันจริงกับ `docs/test-data/2026-08-30_overnight_region_flapping.log` (176 บรรทัด) | — |
| สัญญาที่ข้าม method/event channel | `background_region_monitoring_test.dart` (8 เทสต์) | ว่า Android จะปลุก process ขึ้นมาส่งผลสแกนจริง |
| ตัวรับ broadcast ทั้ง 3 ตัว + `RECEIVE_BOOT_COMPLETED` merge เข้า manifest ของแอปจริง | ตรวจ merged manifest หลัง build | ว่าตัวรับจะถูกเรียกจริง |
| `ExampleApplication` ถูกใช้เป็น `android:name` จริง (ไม่ใช่ `${applicationName}` ค่า default) | ตรวจ merged manifest หลัง build | — |
