### ADR-14 (background monitoring พื้นฐาน) — `observed`

เอกสารกำกับ ไม่ใช่ log):

"วางเครื่องนิ่งข้ามคืน" **ไม่ได้เดินตาม protocol เฉพาะเคสของแต่ละข้อใน

เพราะต้องอาศัยการกระทำของผู้ทดสอบ เช่น ปัดแอปทิ้ง/force-stop/รีบูต/สลับสวิตช์ ที่ log
สองไฟล์นี้ไม่มี) และยังไม่ครบเกณฑ์ทำซ้ำ 2-3 รอบต่อเคสตามกติกาของ

⚠️ **หมายเหตุความต่างของสองไฟล์ที่พบระหว่างตรวจ:** ไฟล์ 09-01 (`_region_flapping`)
เป็นบิลด์ที่**เก่ากว่า** ไฟล์ 09-03 อีกชั้น — บรรทัด `exit` ในไฟล์ 09-01 **ไม่มีคีย์
`sinceLastSeenMs`/`scheduledAtElapsed`/`firedAtElapsed` เลยสักบรรทัด** (62/62) ในขณะที่

(`sinceLastSeenMs` เป็นต้น) จากไฟล์ 09-01 เด็ดขาด มีแค่ไฟล์ 09-03 เท่านั้นที่ใช้คำนวณ
ตัวเลขนี้ได้

### ADR-17 (`reconcile()`) — `code-complete, unverified`

**ยังไม่เคยรันบนเครื่องจริงเลยแม้แต่ครั้งเดียว** — log ทั้งสองไฟล์ข้างบนมาจากบิลด์
**ก่อน** ADR-17 ยืนยันด้วยการรันจริง (4 ก.ย. 2026):

```bash
grep -c "exitReason=" docs/test-data/2026-09-01_android_overnight_region_flapping.log
# → 0
grep -c "exitReason=" docs/test-data/2026-09-03_android_overnight_stale_inside.log
# → 0
```

ทั้งสองไฟล์ไม่มีคีย์ `exitReason=` แม้แต่บรรทัดเดียว — ยืนยันว่าเป็นบิลด์ก่อน ADR-17 จริง
ตามที่คาดไว้ ดูแถว **ข้อ 10 (§11)** ในตารางผลด้านล่าง — สถานะยังคง **ยังไม่ทดสอบ**

## หมายเหตุถาวร — วิธีอ่าน `exitReason=staleReconcile` (ADR-17)

> ⚠️ **`timestampMillis` ของบรรทัดที่มี `exitReason=staleReconcile` คือเวลาที่
> `reconcile()` "ตรวจพบ" ว่าสถานะค้าง ไม่ใช่เวลาที่อุปกรณ์ออกนอกโซนจริง** — สอง
> เวลานี้ต่างกันได้มาก (ในเคสจริงที่เคยเจอคือหลายชั่วโมง เพราะนาฬิกาปลุกถูกระงับไว้
> ทั้งคืน) **ค่าที่บอกความจริงเรื่อง "หายไปนานแค่ไหน" คือ `sinceLastSeenMs` เท่านั้น**
> ห้ามใช้ `timestampMillis` ลบกับเวลาที่คาดว่าออกนอกโซนมาคำนวณ dwell/gap — ต้องอ่าน
> `sinceLastSeenMs` ตรง ๆ จากบรรทัดนั้นเสมอ (ดูรายละเอียดฟิลด์เต็มใน
> `android_background_runbook.md` §0.2 ตาราง "ฟิลด์ในคอลัมน์สัญญาณดิบ" แถว
> `exitReason`) — บันทึกไว้ในไฟล์นี้เพราะเป็นจุดที่คนอ่านผลทีหลังตีความผิดง่ายที่สุด
> ถ้าไม่มีบรรทัดนี้กำกับ

**ยังต้องทำก่อนเปลี่ยนคำของแถว 1/5 เป็นคำที่แข็งแรงกว่า `observed`:**

- **แถว 1 (§2):** ทำซ้ำตาม protocol §2 จริงอีกอย่างน้อย 2-3 รอบ (กด home โดยตั้งใจ + นาฬิกาแยกจับเวลาถอด/ใส่แบต K9P) — ตอนนี้เห็นแค่ 1 รอบและเป็นเหตุการณ์ที่เกิดขึ้นเองระหว่างเก็บ log เคสอื่น ไม่ใช่รอบที่ตั้งใจทดสอบ §2 โดยตรง
- **แถว 5 (§6):** ทำ §6.1 (บังคับ Doze ด้วย `adb`) และ §6.2 (แบบจริง — ถอด/ใส่แบต K9P พร้อมนาฬิกาแยก) ตามขั้นตอนเต็มรูปแบบ แล้ววัด `sinceLastSeenMs` เทียบกับเวลาที่นาฬิกาแยกจับได้จริง — ตัวเลขที่มีตอนนี้มาจากความเงียบตามธรรมชาติของการวางเครื่องนิ่งข้ามคืน ไม่ใช่การวัดที่ควบคุมจุดเริ่มต้น (K9P ออกนอกระยะเมื่อไร) ได้แม่นยำ

## บันทึกรอบทดสอบ

**หมายเหตุ:** ตอนนี้ติดตั้งลงเครื่องได้แล้ว (ตัวบล็อก `INSTALL_FAILED_USER_RESTRICTED`
เดิมหมดอายุไปแล้ว) และมีข้อมูลจริงจากเครื่องอยู่ในตารางผลด้านบนแล้ว (แถว 1 และ 5) —
แต่นั่นคือข้อมูลที่**เกิดขึ้นเองระหว่างเก็บ log ข้ามคืนของเคสอื่น** ไม่ใช่รอบทดสอบที่
ตั้งใจเดินตาม protocol ของแต่ละเคสตามรูปแบบด้านล่างนี้ — ยังไม่มีการบันทึกรอบทดสอบ
แบบตั้งใจตามรูปแบบนี้เลยสักรอบ

รูปแบบที่ต้องบันทึกต่อรอบ:

```
วันที่/เวลา · เคสข้อที่ · Autostart · battOpt · location_mode
processId ก่อน / processId หลัง
เวลาถอดแบต → เวลาได้ exit  = ...
เวลาใส่แบต  → เวลาได้ enter = ...
บรรทัด log ที่เป็นหลักฐาน (คัดลอกมาทั้งบรรทัด)
```
