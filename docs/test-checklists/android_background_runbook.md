# Runbook ทดสอบการทำงานเบื้องหลังบนอุปกรณ์จริง — beacon_kit (Android)

เอกสารนี้คือ **ขั้นตอนลงมือทำ** สำหรับคนที่ถืออุปกรณ์ทดสอบอยู่หน้างาน
เปิดไฟล์นี้ไฟล์เดียวก็ทดสอบได้ครบ ไม่ต้องอ่านเอกสารอื่นระหว่างทำ

ใช้ [`ios_device_test_runbook.md`](./ios_device_test_runbook.md) เป็นแม่แบบ
และปรับให้เข้ากับกลไกที่ต่างกันโดยสิ้นเชิง (ADR-14 หัวข้อ 1)

> ## ⛔ ไฟล์นี้ห้ามบันทึก "สถานะ" เด็ดขาด
>
> **เจ้าของสถานะทั้งหมด (ผ่าน / ไม่ผ่าน / ยังไม่ทดสอบ / ตัวเลขที่วัดได้) คือ
> [`android_background_scanning.md`](./android_background_scanning.md) เท่านั้น**
>
> ไฟล์นี้เป็นเจ้าของ **ขั้นตอน** อย่างเดียว — เหตุผลเดียวกับฝั่ง iOS: ถ้าสองไฟล์
> เขียนสถานะเรื่องเดียวกัน วันหนึ่งจะไม่ตรงกัน แล้วคนอ่านจะเชื่อไฟล์ที่เจอก่อน
> ซึ่งอาจเป็นไฟล์ที่เก่ากว่า (CONTRIBUTING ข้อ 8)

**กติกาการทดสอบที่ใช้กับทุกเคส**

- บันทึกเฉพาะสิ่งที่เห็นจริงบนอุปกรณ์ ห้ามเติมผลที่คาดว่าน่าจะเป็น
- **รอบที่ไม่ยิง event เลยต้องบันทึกด้วย** — ถ้าเก็บแต่รอบที่สำเร็จ ตัวเลขจะดูดี
  เกินจริง แล้วทีม backend จะออกแบบบนสมมติฐานที่ผิด
- ทำซ้ำอย่างน้อย 2-3 รอบก่อนสรุปทุกเคส
- **ทุกผลต้องระบุ: รุ่นเครื่อง / เวอร์ชัน Android / เวอร์ชัน MIUI / สถานะ Autostart /
  สถานะ battery optimization** — ผลที่ไม่ระบุห้าตัวนี้ตรวจสอบย้อนกลับไม่ได้

## 0. ปลดล็อกการติดตั้งก่อน — ขั้นที่ทำให้ทุกอย่างติดอยู่ตอนนี้

`adb install` ถูก MIUI ปฏิเสธด้วย:

```
Failure [INSTALL_FAILED_USER_RESTRICTED: Install canceled by user]
```

**แก้จากฝั่งเครื่องพัฒนาไม่ได้** — ลองแล้วและถูกปฏิเสธ:

```bash
adb shell settings put global adb_install_need_confirm 0
# SecurityException: writing to settings requires android.permission.WRITE_SECURE_SETTINGS
```

**เจ้าของเครื่องต้องเปิดเอง:**

1. ตั้งค่า → เกี่ยวกับโทรศัพท์ → แตะ "เวอร์ชัน MIUI" 7 ครั้ง (เปิด Developer options)
2. ตั้งค่าเพิ่มเติม → ตัวเลือกสำหรับนักพัฒนา → เปิด **"ติดตั้งผ่าน USB"**
   (Install via USB)
3. MIUI จะขอให้ **ล็อกอินบัญชี Xiaomi** และ **ใส่ซิม** ในเครื่องก่อน
4. เปิด **"การแก้จุดบกพร่อง USB (การตั้งค่าความปลอดภัย)"**
   (USB debugging (Security settings)) ด้วย — จำเป็นสำหรับ `adb shell input`
   ที่ใช้กดปุ่มแทนคนในบางขั้นตอน

ยืนยันว่าปลดล็อกแล้วด้วย:

```bash
adb install -r -t packages/beacon_kit/example/build/app/outputs/flutter-apk/app-debug.apk
```

## 0.1 การเตรียมมาตรฐาน (ทำก่อนทุกเคส ห้ามข้าม)

ถ้าข้ามขั้นใดขั้นหนึ่ง ผลที่ได้จะตีความไม่ได้ — ไม่ใช่แค่ "อาจคลาดเคลื่อน"

1. **ถอนการติดตั้งแล้วติดตั้งใหม่**
   ```bash
   adb uninstall com.beaconkit.example
   ```
   สถานะ enter/exit ทั้งหมดเก็บใน SharedPreferences ของแอป (ADR-14 หัวข้อ 1.2)
   ถ้าไม่ล้าง สถานะ "อยู่ในโซน" ที่ค้างจาก build เก่าจะทำให้ไม่มี `enter` ออกมาเลย
   และดูเหมือนกลไกพัง ทั้งที่มันแค่คิดว่าเราอยู่ในโซนอยู่แล้ว

2. **ให้สิทธิ์ครบก่อน**
   ```bash
   adb shell pm grant com.beaconkit.example android.permission.BLUETOOTH_SCAN
   adb shell pm grant com.beaconkit.example android.permission.ACCESS_FINE_LOCATION
   ```
   ยืนยันด้วย:
   ```bash
   adb shell dumpsys package com.beaconkit.example | grep -A2 "runtime permissions"
   ```

3. **เปิดสวิตช์ Location ของระบบ** (คนละเรื่องกับการ grant `ACCESS_FINE_LOCATION`)
   ADR-12 หัวข้อ 1 บันทึกไว้ว่า **ยังไม่ยืนยัน**ว่าจำเป็นหรือไม่ — รอบนี้คือรอบที่
   ต้องตอบ ให้ทดสอบทั้งเปิดและปิด แล้วบันทึกความต่าง
   ```bash
   adb shell settings get secure location_mode
   ```

4. **บันทึกสถานะ MIUI ทั้งสองตัวก่อนเริ่ม** — เป็นตัวแปรที่เปลี่ยนผลได้ทั้งรอบ
   - Autostart: ตั้งค่า → แอป → จัดการแอป → example → **เริ่มทำงานอัตโนมัติ**
   - Battery saver: หน้าเดียวกัน → **ประหยัดแบตเตอรี่** → เลือก "ไม่จำกัด"
   ```bash
   # ยืนยัน battery optimization จากฝั่งระบบ (ไม่ใช่จากหน้าจอ MIUI)
   adb shell dumpsys deviceidle whitelist | grep beaconkit
   ```

5. **กดปุ่ม "เริ่มเฝ้าเบื้องหลัง"** — ไม่ใช่ "Start scan"
   ปุ่ม scan เป็นเส้นทางก้อนที่ 1 ซึ่งผูกอายุการสแกนไว้กับ subscription
   ถ้ากดผิดปุ่ม เคสที่แอปถูกปิดจะไม่มีทางได้ event เลย

6. **ยืนยันสถานะเริ่มต้นก่อนเริ่มจับเวลา**
   - แผง "เฝ้า region เบื้องหลัง (Android)" แสดง "สั่งเฝ้าอยู่หรือไม่: ใช่"
   - "ผลลงทะเบียนล่าสุด" แสดง **สำเร็จ 1** และไม่มีรายการล้มเหลว
   - เห็น `enter` อย่างน้อยหนึ่งครั้ง = ยืนยันว่า beacon อยู่ในระยะจริง

7. **ล้าง log ให้สะอาด** (ปุ่มในหน้า "ดู log") แล้วจดเวลาปัจจุบันไว้

8. **เตรียมนาฬิกาแยก** (มือถืออีกเครื่อง) จดเวลาทุกครั้งที่ถอด/ใส่แบต K9P
   — อย่าใช้เครื่องที่กำลังทดสอบจดเวลา เพราะการปลุกจอมีผลกับ Doze โดยตรง

9. **ถอดสาย USB** ยกเว้นขั้นที่ระบุว่าให้เสียบ
   สายที่เสียบอยู่ทำให้เครื่อง**ไม่เข้า Doze เลย** ซึ่งจะทำให้เคส §5 ไร้ความหมาย

10. **นับ beacon ที่อยู่ในระยะ** แล้วจดไว้

## 0.2 วิธีอ่าน log

ไฟล์ log เขียนโดยโค้ด native
(`example/android/app/src/main/kotlin/com/beaconkit/example/BackgroundEvidenceLog.kt`)
รูปแบบ **เดียวกับฝั่ง iOS เป๊ะ** เพื่อให้เทียบสองแพลตฟอร์มด้วยเครื่องมือชุดเดียวได้

```
timestamp(ISO8601+tz)  processId  event  regionIdentifier  ข้อสรุป  สัญญาณดิบ
```

**ดึงไฟล์ออกมาวิเคราะห์:**

```bash
adb exec-out run-as com.beaconkit.example cat files/region_events.log \
  > /tmp/android_region_events.log
dart run tool/analyze_region_log.dart /tmp/android_region_events.log
```

**ฟิลด์ในคอลัมน์สัญญาณดิบ**

| ฟิลด์ | ความหมาย |
|---|---|
| `everForeground` | process นี้เคยมี Activity ขึ้น resume หรือยัง — **สัญญาณหลักที่เชื่อได้** (คู่แฝดของ `everActive` ฝั่ง iOS) |
| `state` | `resumed` / `started` / `stopped` / `noActivityEver` — สัญญาณดิบ ไม่ใช่ข้อสรุป |
| `importance` | ค่าที่ **ระบบ** จัดให้ process นี้ (`foreground` / `foregroundService` / `service` / `cached` …) — สัญญาณอิสระที่ไม่ได้มาจากการนับ Activity ของเราเอง |
| `doze` | เครื่องอยู่ใน Doze ณ ตอนเขียนบรรทัดหรือไม่ |
| `battOpt` | `ignoring` = ผู้ใช้ปลด battery optimization แล้ว · `optimized` = ยังไม่ปลด |
| `pid` | pid ของ Linux ไว้เทียบกับ `logcat` (**ถูกใช้ซ้ำได้ ไม่ใช่ตัวระบุ process**) |
| `uptime` | process นี้มีอายุกี่วินาที — ใช้ key เดียวกับ iOS เพื่อให้เครื่องมือวิเคราะห์ตัวเดียวอ่านได้ |
| `restoredRegions` | region ที่ **เราเองจำไว้** ณ ตอน launch (มีเฉพาะบรรทัด `launch`) — **ไม่ใช่** `monitoredRegions` ของ iOS ที่ระบบเป็นคนตอบ |

### ตารางแปลผล — ใช้ทุกครั้งก่อนสรุปอะไรก็ตาม

| ที่เห็นใน log | แปลว่า | ทำอะไรต่อ |
|---|---|---|
| ไม่มีบรรทัด `launch` ที่ `processId` ใหม่เลย | ระบบไม่ได้ปลุกแอป | ไล่ที่การลงทะเบียนสแกน / สิทธิ์ / MIUI Autostart / ระยะ beacon — **ไม่ใช่**ที่โค้ดรับ event |
| มี `launch` (`processId` ใหม่) แต่ `restoredRegions=[]` | ถูกปลุกแต่ไฟล์สถานะของเราว่าง | สงสัยว่ามีโค้ดล้างสถานะทิ้ง หรือขั้นเตรียมข้อ 5 ไม่ได้ทำ |
| มี `launch` + region ครบ แต่ไม่มี `enter`/`exit` ตามมา | ถูกปลุกจริงและสถานะยังอยู่ แต่ **event ไปไม่ถึงเครื่องสถานะ** | สงสัย `FLAG_IMMUTABLE` (ADR-14 หัวข้อ 2.1) — ดู §8 |
| `enter`/`exit` + `everForeground=false` | **process ที่ระบบสร้างขึ้นมาเอง = สิ่งที่ต้องการเห็น** | บันทึกลงไฟล์สถานะ |
| `enter`/`exit` + `everForeground=true` | process เดิมยังไม่ตาย | **ยังไม่ได้ทดสอบสิ่งที่ตั้งใจ** ทำใหม่ |

⚠️ **ห้ามสรุปว่า "ฟีเจอร์ไม่ทำงาน" จาก log ที่ว่างเปล่า** — log ว่างเป็นได้ 3 สาเหตุ
ที่มีวิธีแก้คนละทางโดยสิ้นเชิง ตามสามแถวแรกของตารางนี้

### เกณฑ์ตัดสินที่ใช้กับทุกเคส

**ห้ามรายงานว่าผ่าน** จนกว่าจะเห็นบรรทัดที่มีครบทั้งสามอย่างพร้อมกัน:

1. `processId` ที่ **ไม่เคยปรากฏ** ในบรรทัดก่อนหน้าของไฟล์เดียวกัน
2. `conclusion` = `relaunchedFromTerminated`
3. `event` = `enter` หรือ `exit` (ไม่ใช่แค่ `launch`)

## 2. แอปอยู่เบื้องหลัง (กด home) — เคสพื้นฐานที่สุด

**สิ่งที่กำลังพิสูจน์:** ผลสแกนยังมาถึงเมื่อไม่มี UI แต่ process ยังมีชีวิต

1. ทำขั้นเตรียมทั้งหมดใน §0.1
2. กดปุ่ม home (**ห้ามปัดทิ้ง**)
3. ถอดแบต K9P — จดเวลาจากนาฬิกาแยก
4. รอจนได้ notification `exit` — จดเวลา
5. ใส่แบต K9P กลับ — จดเวลา
6. รอจนได้ notification `enter` — จดเวลา
7. เปิดแอป → "ดู log" → ตรวจว่า `processId` **เท่ากับ** ของบรรทัด `launch` ล่าสุด
   (ต้องเป็น process เดิม เพราะแค่กด home ไม่ได้ฆ่า process)
8. จดเวลา enter/exit ที่วัดได้ลงไฟล์สถานะ **ข้อ 1**

**ถ้า `conclusion` เป็น `relaunchedFromTerminated`** แปลว่าระบบฆ่า process ไปแล้ว
ระหว่างทาง — **ไม่ใช่เคสนี้** ให้บันทึกไว้แล้วทำใหม่ (และข้อเท็จจริงที่ว่าระบบฆ่า
process เร็วขนาดนั้นเองก็เป็นข้อมูลที่ควรบันทึก)

## 3. ปัดแอปทิ้งจากรายการแอป — เคสที่สำคัญที่สุด

**สิ่งที่กำลังพิสูจน์:** ระบบสร้าง process ใหม่ขึ้นมาส่งผลสแกนให้จริงหรือไม่
คือเคสที่เทียบตรงกับ B5 ของ iOS

1. ทำขั้นเตรียมทั้งหมดใน §0.1
2. **จด `processId` ปัจจุบัน** จากหน้าจอไว้ก่อน (แสดงในแผงสถานะ)
3. เปิดรายการแอป (ปุ่มสี่เหลี่ยม) แล้ว **ปัดแอปทิ้ง**
4. ยืนยันว่า process ตายจริง:
   ```bash
   adb shell ps -A | grep beaconkit   # ต้องไม่เจออะไร
   ```
   **ขั้นนี้ห้ามข้าม** — ถ้า process ยังอยู่ ผลที่ได้จะเป็นเคส §2 ไม่ใช่เคสนี้
5. ถอดแบต K9P — จดเวลา · รอ 2 นาที · ใส่กลับ — จดเวลา
6. รอ notification `enter`
7. ดึง log ออกมาตรวจ **โดยไม่ต้องเปิดแอป**:
   ```bash
   adb exec-out run-as com.beaconkit.example cat files/region_events.log | tail -20
   ```
   (ถ้า `run-as` ใช้ไม่ได้ ให้เปิดแอปแล้วดูหน้า "ดู log" แทน — แต่ให้ดูก่อนว่า
   บรรทัดที่สนใจมี `processId` ต่างจากที่จดไว้ในข้อ 2)
8. **เกณฑ์ผ่าน:** เห็นบรรทัด `enter` ที่ `processId` ต่างจากข้อ 2 **และ**
   `conclusion=relaunchedFromTerminated`
9. บันทึกลงไฟล์สถานะ **ข้อ 2** พร้อมเวลาที่วัดได้

**ทำซ้ำ 3 รอบ** และบันทึกรอบที่ไม่มี event ด้วย

## 4. force-stop — คาดว่าไม่รอด ต้องยืนยันว่าไม่รอดจริง

**สิ่งที่กำลังพิสูจน์:** ข้อสรุปจากเอกสาร (ADR-14 หัวข้อ 1.4) ตรงกับของจริงหรือไม่

**เคสนี้คาดว่าจะไม่มี event เลย และนั่นคือผลลัพธ์ที่ถูกต้อง** — การยืนยันว่ากลไก
หยุดจริงหลัง force-stop มีค่าเท่ากับการยืนยันว่ามันทำงานในเคสอื่น เพราะมันคือสิ่งที่
ต้องเขียนลงสัญญาต่อผู้ใช้ SDK

1. ทำขั้นเตรียมทั้งหมดใน §0.1
2. จด `processId` ปัจจุบัน
3. ตั้งค่า → แอป → example → **บังคับหยุด** (หรือ `adb shell am force-stop com.beaconkit.example`)
4. ถอด/ใส่แบต K9P — จดเวลา
5. **รอ 10 นาที** โดยไม่แตะเครื่องเลย
6. ตรวจว่ามี process ขึ้นมาหรือไม่:
   ```bash
   adb shell ps -A | grep beaconkit
   ```
7. เปิดแอปแล้วดู log — ตรวจว่ามีบรรทัดใหม่ระหว่างช่วงนั้นหรือไม่
8. บันทึกลงไฟล์สถานะ **ข้อ 3**

**สิ่งที่ต้องบันทึกเพิ่ม:** หลังเปิดแอปเองแล้ว **การเฝ้ากลับมาทำงานอัตโนมัติหรือไม่**
— แผงสถานะยังบอกว่า "สั่งเฝ้าอยู่: ใช่" (เพราะเราจำไว้ในไฟล์) แต่การลงทะเบียนจริง
อาจหายไปแล้ว นี่คือความต่างที่ ADR-14 หัวข้อ 1.2 เตือนไว้ และเป็นจุดที่ต้องตัดสินใจ
ว่าจะต้องลงทะเบียนใหม่ทุกครั้งที่แอปเปิดหรือไม่

---

## 5. รีบูตเครื่องแล้วไม่เปิดแอป

**สิ่งที่กำลังพิสูจน์:** `BootCompletedReceiver` ลงทะเบียนใหม่ได้จริงหรือไม่

1. ทำขั้นเตรียมทั้งหมดใน §0.1 · จด `processId` ปัจจุบัน
2. `adb reboot`
3. **ปลดล็อกเครื่องหนึ่งครั้ง** (จำเป็น — `BOOT_COMPLETED` ส่งหลังผู้ใช้ปลดล็อก
   ตาม `Intent.java:2818-2821`) แล้ว **ไม่เปิดแอป**
4. รอ 2 นาที · ถอด/ใส่แบต K9P — จดเวลา
5. รอ notification `enter`
6. ดึง log ออกมาตรวจ **โดยไม่เปิดแอป** (คำสั่งใน §3 ข้อ 7)
7. **สิ่งที่ต้องดูเป็นพิเศษ:** บรรทัด `launch` หลังรีบูตต้องมี
   `restoredRegions=[k9p-default]` — ถ้าว่าง แปลว่าตัวรับ boot ทำงานแต่ไฟล์สถานะหาย
   ซึ่งเป็นคนละปัญหากับตัวรับไม่ทำงาน
8. บันทึกลงไฟล์สถานะ **ข้อ 4**

**ทดสอบเพิ่มอีกรอบแบบไม่ปลดล็อก:** รีบูตแล้ว**ทิ้งไว้ที่หน้าล็อก** 10 นาที
ถอด/ใส่แบต K9P แล้วดูว่ามี event หรือไม่ — คาดว่าไม่มี (ADR-14 หัวข้อ 1.5)
**ยืนยันว่าไม่มีจริงคือผลลัพธ์ที่ถูกต้อง** ไม่ใช่ความล้มเหลว

## 6. Doze — ทิ้งไว้นาน ๆ ไม่แตะเครื่อง

**สิ่งที่กำลังพิสูจน์:** BLE scan ผ่าน `PendingIntent` รอด Doze หรือไม่
เอกสารทางการ**ไม่พูดถึง BLE เลย** (ADR-14 หัวข้อ 2.4) จึงต้องวัดเอง

### 6.1 แบบเร่ง Doze ด้วย adb (ทำก่อน เพราะเร็ว)

```bash
# ต้องถอดสาย USB จริง ๆ ไม่ได้ ใช้คำสั่งจำลองแทน
adb shell dumpsys battery unplug
adb shell dumpsys deviceidle enable
adb shell dumpsys deviceidle force-idle
adb shell dumpsys deviceidle get deep      # ต้องได้ IDLE
```

จากนั้นถอด/ใส่แบต K9P แล้วรอ · ตรวจ log ว่า `doze=true` ปรากฏในบรรทัดหรือไม่

คืนค่าเมื่อเสร็จ:
```bash
adb shell dumpsys deviceidle unforce
adb shell dumpsys battery reset
```

### 6.2 แบบจริง (ต้องทำด้วย เพราะแบบเร่งไม่เหมือนของจริงทุกอย่าง)

1. ทำขั้นเตรียมทั้งหมดใน §0.1 · **ถอดสาย USB**
2. ปัดแอปทิ้ง · วางเครื่องนิ่ง จอดับ **ห้ามแตะอย่างน้อย 1 ชั่วโมง**
3. ถอด/ใส่แบต K9P (ใช้นาฬิกาแยกจดเวลา) — อย่าปลุกจอเครื่องทดสอบ
4. รออีก 30 นาที แล้วค่อยเปิดเครื่องดู
5. บันทึกลงไฟล์สถานะ **ข้อ 5**

**สิ่งที่ต้องวัดโดยเฉพาะ:** เวลาที่ใช้ประกาศ `exit` เทียบกับค่า N ที่ตั้งไว้
(30 วินาที) — ADR-14 หัวข้อ 1.3 คาดว่าจะช้าถึงระดับ ~15 นาทีใน Doze
**ตัวเลขจริงคือสิ่งที่รอบนี้ต้องได้มา**

**ทำการทดสอบข้ามคืนด้วย** เหมือนที่ทำกับ iOS (ADR-11) แล้วรันตัววิเคราะห์ตัวเดียวกัน
เพื่อเทียบ flap ของสองแพลตฟอร์มบนข้อมูลที่คำนวณด้วยวิธีเดียวกัน

## 7. MIUI Autostart — เปิด vs ปิด

**สิ่งที่กำลังพิสูจน์:** ข้อสงสัยที่ ADR-12 หัวข้อ 6 บันทึกไว้ว่า
**"ยังไม่ยืนยันด้วยตัวเอง"** — ตอนนี้มีเครื่องแล้วจึงยืนยันได้จริง

ทำเคส §3 (ปัดแอปทิ้ง) **สองรอบ** ในสภาพที่ต่างกันแค่ตัวแปรเดียว:

| รอบ | Autostart | Battery saver |
|---|---|---|
| A | **ปิด** | ไม่จำกัด |
| B | **เปิด** | ไม่จำกัด |

**ห้ามเปลี่ยนสองตัวแปรพร้อมกัน** — ถ้าเปลี่ยนทั้งคู่แล้วผลต่างกัน จะไม่รู้ว่าตัวไหน
เป็นเหตุ ซึ่งทำให้ทั้งรอบทดสอบไร้ค่า

ทำซ้ำอย่างน้อย 3 รอบต่อสภาพ แล้วบันทึก **จำนวนรอบที่ได้ event / จำนวนรอบทั้งหมด**
ลงไฟล์สถานะ **ข้อ 6** — ตัวเลขนี้คือสิ่งที่ตอบได้ว่า Autostart จำเป็นแค่ไหน

**ทำเคส battery optimization แยกอีกชุด** ด้วยวิธีเดียวกัน (ตัวแปรเดียว):

```bash
# ปลดยกเว้น (สภาพ optimized)
adb shell dumpsys deviceidle whitelist -com.beaconkit.example
# ใส่ยกเว้น (สภาพ ignoring)
adb shell dumpsys deviceidle whitelist +com.beaconkit.example
```

ค่านี้ปรากฏใน log ทุกบรรทัดที่ฟิลด์ `battOpt=` จึงตรวจย้อนกลับได้เสมอ

## 8. ยืนยัน `FLAG_MUTABLE` ด้วยการทดลอง

**สิ่งที่กำลังพิสูจน์:** ข้อสรุปใน ADR-14 หัวข้อ 2.1 เป็น **การต่อประโยคจากสองหน้า
เอกสาร** ไม่ใช่ประโยคเดียวที่ Android เขียนตรง ๆ จึงต้องพิสูจน์ด้วยการทดลอง

1. ทำเคส §2 (กด home) ให้ได้ `enter` สำเร็จก่อน — เป็นกลุ่มควบคุม
2. แก้ `BackgroundRegionMonitor.scanPendingIntent` ชั่วคราวจาก `FLAG_MUTABLE`
   เป็น `FLAG_IMMUTABLE` แล้ว build/ติดตั้งใหม่
3. ทำเคส §2 ซ้ำในสภาพเดียวกันทุกอย่าง
4. **สิ่งที่คาดว่าจะเห็น:** ไม่มี `enter` เลย — และถ้าต้องการหลักฐานตรงกว่านั้น
   ให้ดู `logcat` ว่ามี broadcast มาถึงหรือไม่:
   ```bash
   adb logcat | grep -i "BeaconScanReceiver\|beacon_kit"
   ```
5. **คืนค่ากลับเป็น `FLAG_MUTABLE` ทันทีที่จบ** — และยืนยันว่าคืนแล้วด้วย
   `git diff` ก่อนทำเคสอื่นต่อ
6. บันทึกผลลงไฟล์สถานะ **ข้อ 7**

⚠️ ถ้าผลออกมาว่า `FLAG_IMMUTABLE` **ก็ใช้ได้** ต้องแก้ ADR-14 หัวข้อ 2.1 ทันที
และเปลี่ยนโค้ดไปใช้ `FLAG_IMMUTABLE` ตามคำแนะนำของเอกสาร
(`PendingIntent.java:278`: "It is strongly recommended to use `FLAG_IMMUTABLE`")

## 9. สวิตช์ Location ของระบบ

**สิ่งที่กำลังพิสูจน์:** คำถามที่ ADR-12 หัวข้อ 1 ทิ้งไว้ว่า
"ผู้ใช้ต้องเปิดสวิตช์ Location ของระบบด้วยหรือไม่ (คนละเรื่องกับการ grant
`ACCESS_FINE_LOCATION`)" — ไม่พบประโยคที่ระบุตรง ๆ ในเอกสารที่ตรวจ

ทำเคส §2 สองรอบ ต่างกันแค่:

```bash
adb shell settings get secure location_mode   # จดค่าเดิมไว้ก่อน
```

- รอบ A: สวิตช์ Location **เปิด**
- รอบ B: สวิตช์ Location **ปิด** (ปิดจากแถบตั้งค่าด่วน)

บันทึกลงไฟล์สถานะ **ข้อ 8** — ต้องบันทึกทั้งกรณีที่สแกนไม่เจอเลย และกรณีที่
`startBackgroundRegionMonitoring` คืน error

## 10. เพดานจำนวน region ที่ลงทะเบียนพร้อมกัน

**สิ่งที่กำลังพิสูจน์:** ADR-14 หัวข้อ 4.1 บันทึกว่ายังไม่รู้เพดาน — ADR-8 กำหนด
region ไว้ 20 อัน ซึ่งบนกลไกนี้แปลว่า **20 การลงทะเบียนพร้อมกัน**

1. แก้ example app ชั่วคราวให้ส่ง region 20 อัน (identifier ต่างกัน major ต่างกัน)
2. กด "เริ่มเฝ้าเบื้องหลัง" แล้วดูตาราง "ผลลงทะเบียนล่าสุด"
3. บันทึก **จำนวนที่สำเร็จ** และ **error code ของอันที่ล้มเหลว**
   (คาดว่าจะเป็น `SCAN_FAILED_OUT_OF_HARDWARE_RESOURCES` แต่ยังไม่ยืนยัน)
4. ถ้าสำเร็จครบ 20 ให้ลองเพิ่มเป็น 30 เพื่อหาเพดานจริง
5. บันทึกลงไฟล์สถานะ **ข้อ 9** พร้อม **คืนโค้ดกลับเป็นเดิม**
