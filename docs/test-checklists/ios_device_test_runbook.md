# Runbook ทดสอบบนอุปกรณ์จริง — beacon_kit (iOS)

เอกสารนี้คือ **ขั้นตอนลงมือทำ** สำหรับคนที่ถืออุปกรณ์ทดสอบอยู่หน้างาน
เปิดไฟล์นี้ไฟล์เดียวก็ทดสอบได้ครบ ไม่ต้องอ่านเอกสารอื่นระหว่างทำ

> ## ⛔ ไฟล์นี้ห้ามบันทึก "สถานะ" เด็ดขาด
>
> **เจ้าของสถานะทั้งหมด (ผ่าน / ไม่ผ่าน / ยังไม่ทดสอบ / ตัวเลขที่วัดได้) คือ
> [`ios_broadcast_scanning.md`](./ios_broadcast_scanning.md) เท่านั้น**
>
> ไฟล์นี้เป็นเจ้าของ **ขั้นตอน** อย่างเดียว — ห้ามเขียนคำว่า "ผ่าน" "ไม่ผ่าน"
> "verified" หรือตัวเลขที่วัดได้ลงในไฟล์นี้ ให้อ้างหมายเลขข้อในไฟล์สถานะแทน
>
> **ทำไมถึงห้ามเข้มขนาดนี้:** ถ้าสองไฟล์เขียนสถานะเรื่องเดียวกัน วันหนึ่งจะไม่ตรงกัน
> แล้วคนอ่านจะเชื่อไฟล์ที่เจอก่อน ซึ่งอาจเป็นไฟล์ที่เก่ากว่า — ปัญหานี้แพงกว่าความ
> ไม่สะดวกที่ต้องเปิดสองไฟล์มาก (CONTRIBUTING ข้อ 8)
>
> ตรวจอัตโนมัติได้ด้วย:
> ```bash
> grep -nE '(^|[^ก-๙a-zA-Z])(ผ่าน|ไม่ผ่าน|verified|unverified)' \
>   docs/test-checklists/ios_device_test_runbook.md
> ```
> ต้องไม่เจออะไรนอกจากบรรทัดในกล่องนี้เอง

**กติกาการทดสอบที่ใช้กับทุกเคส**

- บันทึกเฉพาะสิ่งที่เห็นจริงบนอุปกรณ์ ห้ามเติมผลที่คาดว่าน่าจะเป็น
- **รอบที่ไม่ยิง event เลยต้องบันทึกด้วย** — ถ้าเก็บแต่รอบที่สำเร็จ ตัวเลขจะดูดี
  เกินจริง แล้วทีม backend จะออกแบบบนสมมติฐานที่ผิด
- ทำซ้ำอย่างน้อย 2-3 รอบก่อนสรุปทุกเคส เพราะเวลาที่วัดได้แกว่งมาก
- เคสที่ยังไม่ได้ทดสอบ ห้ามกรอกผลลงไฟล์สถานะเพราะ "น่าจะทำงานได้"
- ช่องที่เขียนว่า _(ผู้ทดสอบกรอก)_ ในไฟล์สถานะ ให้คนทดสอบเป็นคนกรอกเท่านั้น

## 0. การเตรียมมาตรฐาน (ทำก่อนทุกเคส ห้ามข้าม)

ถ้าข้ามขั้นใดขั้นหนึ่ง ผลที่ได้จะตีความไม่ได้ — ไม่ใช่แค่ "อาจคลาดเคลื่อน"

1. **ลบแอปออกจากเครื่องแล้วติดตั้งใหม่**
   region monitoring ผูกกับแอปและ**อยู่ข้าม process** ถ้าไม่ลบ อาจมี region ค้าง
   จาก build เก่าจนแยกไม่ออกว่า event มาจาก region ไหน (ดูภาคผนวกข้อ 4)
2. **ติดตั้งด้วย release หรือ profile build เท่านั้น — ห้าม debug**
   debugger ที่เกาะอยู่ทำให้พฤติกรรมตอน terminate/relaunch ไม่ตรงกับของจริง
   (เหตุผลเต็มใน CONTRIBUTING ข้อ 6) · ใน VS Code เลือกจาก dropdown ของ
   `.vscode/launch.json`
3. **ให้สิทธิ์ Location เป็น "Always"**
   ยืนยันด้วยตาที่ Settings → Privacy & Security → Location Services → ชื่อแอป
   ต้องขึ้น **Always** ไม่ใช่ "While Using the App" (iOS มักให้ While Using ก่อน
   ต้องเลื่อนเป็น Always เอง เพราะ iOS ไม่ให้แอปขอ Always ซ้ำ)
4. **อนุญาต Notification**
5. **กด "Start region monitoring"** — ไม่ใช่ "Start scan"
   ปุ่ม scan เป็น ranging ซึ่งผูกอายุ region ไว้กับ subscription ถ้ากดผิดปุ่ม
   เคสที่แอปถูก terminate จะไม่มีทางได้ event
6. **ยืนยันสถานะเริ่มต้นก่อนเริ่มจับเวลา**
   - เห็นบรรทัด `launch` ใน log และ `monitoredRegions` **ไม่ว่าง**
   - เห็น event ยืนยันว่าตอนนี้อยู่ "ข้างใน" region แล้ว
7. **ล้าง log** ให้สะอาด แล้วจดเวลาปัจจุบันไว้
8. **เตรียมนาฬิกาแยก** (มือถืออีกเครื่อง) จดเวลาทุกครั้งที่ถอด/ใส่แบต K9P
   — อย่าใช้เครื่องที่กำลังทดสอบจดเวลา เพราะการปลุกจอมีผลกับบางเคส
9. **ถอดสายที่ต่อกับ Mac** ถ้ามี
10. **นับ beacon ที่อยู่ในระยะ** แล้วจดไว้ — มีผลกับ exit โดยตรง (ภาคผนวกข้อ 3)

## 0.1 วิธีอ่าน log

ไฟล์ log เขียนโดยโค้ด native (`example/ios/Runner/BackgroundEvidenceLog.swift`)
แต่ละบรรทัดคั่นด้วย TAB **6 คอลัมน์**:

```
timestamp(ISO8601+tz)  processId  event  regionIdentifier  ข้อสรุป  สัญญาณดิบ
```

**คอลัมน์ `processId` เพิ่มเข้ามาใน ADR-14** — เป็นค่าสุ่ม 8 ตัวอักษรต่อ process
เขียนเหมือนกันทั้ง iOS และ Android **สองบรรทัดที่ `processId` ต่างกันมาจากคนละ
process แน่นอน ไม่ต้องเดาจาก `uptime` อีกต่อไป**

ไฟล์ log ที่เก็บไว้ก่อนหน้านี้ยังเป็น 5 คอลัมน์และ **ห้ามแก้** — ตัวอ่านทั้งหมด
(หน้า "ดู log" และ `tool/analyze_region_log.dart`) รับได้ทั้งสองรูปแบบ

**ฟิลด์ในคอลัมน์สัญญาณดิบ**

| ฟิลด์ | ความหมาย |
|---|---|
| `everActive` | process นี้เคยผ่าน `applicationDidBecomeActive` หรือยัง — **สัญญาณหลักที่เชื่อได้** |
| `state` | สถานะแอปตอนเกิด event (`foreground` / `background` / `inactive`) |
| `uptime` | process นี้มีอายุกี่วินาทีแล้ว |
| `launchKey` | มี location launch key มาด้วยหรือไม่ — **ไม่มีข้อมูล ไม่ใช่ "สัญญาณสนับสนุน"** แอปนี้ใช้ UIScene lifecycle จึง `launchOptions` ทั้ง dictionary เป็น `nil` เสมอ (ยืนยันจากเอกสาร Apple — ARCHITECTURE.md ADR-16 หัวข้อ 2) ค่านี้จึงเป็น `false` เสมอไม่ว่าความจริงจะเป็นอะไร ห้ามใช้กู้ข้อสรุปอะไรทั้งสิ้น (ภาคผนวกข้อ 6) |
| `monitoredRegions` | รายชื่อ region ที่ระบบลงทะเบียนไว้ ณ ตอน launch (มีเฉพาะบรรทัด `launch`) — **ระบบเป็นคนตอบ** ต่างจาก `restoredRegions=` ฝั่ง Android ที่เราจำเอง (ADR-14 หัวข้อ 1.2) |

**ตารางแปลผลสำหรับเคสที่แอปถูก terminate — ใช้ทุกครั้งก่อนสรุปอะไรก็ตาม**

| ที่เห็นใน log | แปลว่า | ทำอะไรต่อ |
|---|---|---|
| ไม่มีบรรทัด `launch` ใหม่เลย | iOS ไม่ได้ปลุกแอป | ไล่ที่ region / สิทธิ์ Always / ระยะ beacon — ไม่ใช่ที่โค้ดรับ event |
| มี `launch` แต่ `monitoredRegions=[]` | ถูกปลุกแต่ไม่มี region ค้างในระบบ | สงสัยว่ามีโค้ดไปล้าง region ทิ้ง หรือขั้นเตรียมข้อ 5 ไม่ได้ทำ |
| มี `launch` + region ครบ แต่ไม่มี `enter`/`exit` ตามมา | ถูกปลุกจริงและ region ยังอยู่ แต่ **event ไปไม่ถึง handler** | ไล่ที่ delegate / เส้นทางส่ง event — คนละเรื่องกับสองแถวบน |
| `enter`/`exit` + `everActive=false` + `state=background` | process ใหม่ที่ระบบสร้างขึ้นมาเอง = สิ่งที่ต้องการเห็น | ยืนยันซ้ำว่า `processId` ต่างจากบรรทัดก่อนหน้าจริง แล้วบันทึกลงไฟล์สถานะ |
| `enter`/`exit` + `everActive=true` | process เดิมยังไม่ตาย | **ยังไม่ได้ทดสอบสิ่งที่ตั้งใจ** ทำใหม่ |

⚠️ **ห้ามสรุปว่า "ฟีเจอร์ไม่ทำงาน" จาก log ที่ว่างเปล่า** — log ว่างเป็นได้ 3 สาเหตุ
ที่มีวิธีแก้คนละทางโดยสิ้นเชิง ตามสามแถวแรกของตารางนี้

## 2. เคสข้อ 14 — ระบบฆ่าแอปเองเพราะหน่วยความจำ

**ทำไมอยู่บนสุด:** ผู้ใช้ทั่วไปแทบไม่ปัดแอปทิ้งเอง แต่ iOS ฆ่าแอปเพราะหน่วยความจำ
ไม่พอตลอดเวลา — นี่คือเส้นทางที่เกิดกับผู้ใช้จริงมากที่สุด และเป็น**คนละเส้นทางของ OS**
กับการที่ผู้ใช้ปัดแอปทิ้ง (ข้อ 12) จะเหมารวมว่าผลเหมือนกันไม่ได้

**ข้อจำกัด:** บังคับให้ระบบฆ่าแอปแบบเจาะจงไม่ได้ ต้องสร้างแรงกดดันหน่วยความจำแล้วรอ

### ⚠️ ต้องทำก่อนเริ่มเคสนี้ (prerequisite — ยังไม่ได้ทำ)

ตอนนี้เราแยก "process ใหม่" ออกจาก "process เดิม" ด้วย `uptime` ซึ่งตีความได้ไม่ชัด
(process เดิมที่เพิ่งถูกปลุกจาก suspend ก็มี uptime สั้นได้)

**ควรเพิ่ม process UUID (สุ่มหนึ่งค่าตอน process เริ่ม) ลงทุกบรรทัด log** — ถ้า UUID
เปลี่ยน แปลว่าเป็น process ใหม่แน่นอน ไม่ต้องเดาจากตัวเลขเวลา

> **นี่เป็นงานแก้โค้ด ยังไม่ได้ทำ และจะทำเป็น PR แยก** — บันทึกไว้ตรงนี้เพราะเป็น
> เงื่อนไขที่ทำให้ผลของเคสนี้ตีความได้แน่นอน ถ้าทดสอบก่อนมีสิ่งนี้ ให้ระวังว่าการ
> อ่านผลจะอาศัยการตีความ `uptime` ซึ่งเถียงได้

### ขั้นตอน

1. ทำการเตรียมมาตรฐาน (§0) ให้ครบทุกข้อ
2. **กด home ให้แอปไปเบื้องหลัง — อย่าปัดทิ้ง** ← ความต่างสำคัญจากข้อ 12
3. สร้างแรงกดดันหน่วยความจำ เลือกอย่างใดอย่างหนึ่ง:
   - **แบบเร่ง (20-30 นาที):** ถ่ายวิดีโอ 4K ยาว ๆ, เปิดแผนที่โหมด 3D, เปิด Safari
     หลายสิบแท็บ, เล่นเกมกราฟิกหนัก สลับกันไปมา
   - **แบบธรรมชาติ:** ทิ้งไว้ข้ามคืน ใช้เครื่องตามปกติ
4. ถอดแบต K9P → จดเวลา → รอ 3-5 นาที
5. ใส่แบตกลับ → จดเวลา → รอ 3-5 นาที
6. เปิดแอปดู log

### เกณฑ์อ่านผล

ใช้ตารางแปลผลใน §0.1 ก่อน จากนั้น:

| ที่เห็น | แปลว่า |
|---|---|
| `uptime` น้อย (ไม่กี่วินาที) + `everActive=false` | process ใหม่ที่ระบบสร้าง = สิ่งที่ต้องการเห็น |
| `uptime` เป็นชั่วโมง | process เดิมยังไม่ตาย — **ยังไม่ได้ทดสอบสิ่งที่ตั้งใจ** ต้องกดดันหน่วยความจำมากกว่านี้แล้วทำใหม่ |
| ไม่มีบรรทัดใหม่เลย | ต้องแยกให้ได้ก่อนว่าแอปตายจริงหรือยัง **ก่อน**จะสรุปอะไร |

## 3. เคสข้อ 13 — เครื่องล็อกอยู่ตอนถูกปลุก (Data Protection)

**ทำไมสำคัญ:** เป็นสถานการณ์จริงเกือบทั้งหมด (มือถืออยู่ในกระเป๋า จอดับ ลูกค้าเดินเข้า
สาขา) และเป็นเคสที่ **Data Protection อาจบล็อกการเขียนไฟล์ log** — แอปตื่นจริงแต่ไม่มี
หลักฐาน ซึ่งจะทำให้สรุปผิดว่าฟีเจอร์ไม่ทำงาน

### ขั้นตอน

1. ทำการเตรียมมาตรฐาน (§0) ให้ครบ
2. ปัดแอปทิ้งจาก app switcher
3. **กดปุ่ม power ให้จอดับและล็อกเครื่อง** — อย่าแตะเครื่องอีกเลยจนจบการทดสอบ
4. ถอดแบต K9P → จดเวลา → รอ 3-5 นาที (สังเกตว่ามี notification โผล่บนหน้าจอล็อกไหม)
5. ใส่แบตกลับ → จดเวลา → รอ 3-5 นาที
6. ปลดล็อกเครื่อง เปิดแอป ดู log

### เกณฑ์อ่านผล

| ที่เห็น | แปลว่า |
|---|---|
| notification มา **และ** log มีบรรทัดครบ | ได้ทั้งการปลุกและหลักฐาน |
| notification มา **แต่ log ว่าง** | **Data Protection บล็อกการเขียนไฟล์** ต้องกลับไปแก้ protection class — ไม่ใช่ปัญหาของ region monitoring |
| ไม่มีทั้งสองอย่าง | แอปไม่ถูกปลุกตอนล็อก — ข้อจำกัดร้ายแรง ต้องสืบต่อ |

### เคสย่อย 13b — รีบูตแล้วไม่ปลดล็อกเลย

รีบูตเครื่อง แล้ว**ไม่ปลดล็อกสักครั้ง** จากนั้นถอด/ใส่แบต

ทดสอบขอบเขตของ `NSFileProtectionCompleteUntilFirstUserAuthentication` โดยตรง
เอกสาร Apple ระบุเองว่า region monitoring "can only occur after the user unlocks the
device after a reboot" — ถ้าผลออกมาตามที่เอกสารบอก ให้บันทึกเป็น**ข้อจำกัดที่รู้แล้ว**
ไม่ใช่บั๊ก

## 4. เคสข้อ 9 — region ซ้อนทับกัน (broad + specific)

**ทำไมสำคัญ:** เป็น open question ที่ค้างใน ARCHITECTURE.md ADR-8 ตั้งแต่ออกแบบ และ
**บล็อกการเขียน dedupe logic อยู่** — ถ้า event มาซ้ำสองครั้งต่อการเข้าหนึ่งครั้ง สถิติ
ฝั่ง backend จะผิดทั้งหมดโดยไม่มีใครรู้ตัวจนไปเทียบกับข้อมูลจริง

### ขั้นตอน

1. ทำการเตรียมมาตรฐาน (§0)
2. ลงทะเบียน **2 region พร้อมกัน** ที่แมตช์ K9P ตัวเดียวกัน:
   - region กว้าง: UUID อย่างเดียว
   - region เจาะจง: UUID + major ของ K9P ตัวนั้น
3. **ยืนยันว่า `monitoredRegions` มี 2 รายการจริง** ก่อนเริ่มจับเวลา
4. ถอดแบต → รอ → ใส่กลับ → รอ
5. **นับจำนวนบรรทัดใน log ต่อ 1 เหตุการณ์**

### เกณฑ์อ่านผล

| ที่เห็น | แปลว่า |
|---|---|
| 1 บรรทัดต่อเหตุการณ์ | iOS รวมให้แล้ว ไม่ต้องเขียน dedupe |
| 2 บรรทัด (คนละ region identifier) | ต้องเขียน dedupe logic และตัดสินใจว่าจะเชื่อ region ไหนเป็นหลัก |

**ไม่ว่าผลออกมาแบบไหน ให้ไปปิด open question ใน ADR-8 ด้วย** — ตอนนี้ ADR-8 ห้ามเขียน
dedupe ที่ตั้งอยู่บนข้อสมมติข้อใดข้อหนึ่ง จนกว่าจะมีผลจริง

### เคสย่อยถ้ามี K9P 2 ตัว

ถอดแบตตัวที่ตรงกับ region เจาะจง แต่อีกตัวยังเปิดอยู่ — region เจาะจงควรยิง exit
ส่วน region กว้างควรยัง "อยู่ข้างใน" (ดูภาคผนวกข้อ 3 ประกอบ)

## 5. เคสข้อ 10 — ไม่มีอินเทอร์เน็ต

**ทำไมสำคัญ:** เอกสาร Apple ของ `startMonitoring(for:)` ระบุว่า region monitoring
ต้องการ network connectivity เพื่อรายงานได้ทันเวลา — สาขาจริงมีจุดอับสัญญาณเยอะ
(ชั้นใต้ดิน ห้องเย็น โกดัง)

### ขั้นตอน

1. ทำการเตรียมมาตรฐาน (§0) ตอนที่ยังมีเน็ตปกติ
2. ปัดแอปทิ้ง
3. **เปิด Airplane Mode → แล้วเปิด Bluetooth กลับ**
   ⚠️ Airplane Mode ปิดบลูทูธไปด้วย ต้องเปิดกลับเองใน Control Center ไม่งั้นจะกลาย
   เป็นการทดสอบว่า "ปิดบลูทูธแล้วใช้ไม่ได้" ซึ่งไม่ใช่สิ่งที่ต้องการรู้
4. ถอดแบต → จดเวลา → รอ (เผื่อถึง 10 นาที) → ใส่กลับ → รอ
5. เปิดแอปดู log

### เกณฑ์อ่านผล

เคสนี้**ไม่ใช่การตัดสินว่าใช้ได้หรือไม่ได้** แต่เป็นการ**วัดระดับความเสื่อม** — เทียบ
เวลาที่วัดได้กับค่าอ้างอิงของข้อ 12 ในไฟล์สถานะ ถ้าช้าลงมากหรือไม่มาเลย ให้บันทึกเป็น
ข้อจำกัดที่ต้องแจ้งทีมธุรกิจ เพราะกระทบการวางแผนใช้งานจริงในสาขา

## 6. เคสข้อ 6 (ส่วนที่เหลือ) — Eddystone UID / TLM frame

parser เขียนไว้ครบ 3 frame type (UID / URL / TLM) ส่วนที่เหลือของข้อ 6 คือการยืนยัน
frame ชนิด UID และ TLM กับของจริง (สถานะปัจจุบันของแต่ละชนิดดูที่ข้อ 6 ในไฟล์สถานะ)

**ข้อติดขัด:** K9P ต้องถูกตั้งค่าให้ broadcast frame เหล่านั้น ซึ่งต้องใช้ GATT ที่ยัง
ไม่ implement

**ทางออกที่ไม่ต้องรอ GATT:** ไม่จำเป็นต้องใช้ K9P — ใช้อุปกรณ์อะไรก็ได้ที่กระจาย
Eddystone UID/TLM เช่น **มือถือ Android หนึ่งเครื่องกับแอปจำลอง beacon** ตั้งให้
broadcast Eddystone UID แล้ว TLM ได้เลย ทดสอบ parser ครบทั้ง 3 frame type โดยไม่ต้อง
แตะ K9P

### ขั้นตอน

1. ตั้งอุปกรณ์จำลองให้ broadcast Eddystone UID
2. เปิดแอป กด **"Start scan"** (เส้นทาง raw CoreBluetooth — คนละปุ่มกับเคสอื่นใน
   runbook นี้) ดูว่า decode ออกมาถูกไหม
3. เปลี่ยนเป็น TLM frame ทำซ้ำ
4. **จับ raw hex ด้วย nRF Connect ระหว่างทดสอบ**

⚠️ **ถ้าจับ raw hex ได้ ให้บันทึกเป็น fixture `source: captured`** ตามกฎใน
`docs/fixtures/README.md` — ตอนเจอ URL frame ครั้งก่อนไม่ได้จับ byte ดิบไว้ จึงไม่มี
fixture จริงไว้ทำ regression test

**ห้ามสร้าง fixture `captured` ย้อนหลังจากค่าที่ decode แล้ว** — ผิดกฎ และทำให้ข้อมูล
ที่ดูน่าเชื่อถือกลายเป็นของปลอมที่ตรวจไม่เจอ

## 7. เคสข้อ 15 — เก็บสถิติ foreground exit

**ทำไมต้องทำ:** ตัวเลขที่บันทึกไว้ในไฟล์สถานะตอนนี้มาจากการวัดไม่กี่รอบ ซึ่งไม่พอให้
ทีม backend ใช้กำหนด timeout — และ exit มีช่วงกว้างกว่า enter มาก

### ขั้นตอน

ทำซ้ำ **5 รอบต่อเงื่อนไข** (foreground / background × enter / exit) แล้วบันทึก:

- ค่าต่ำสุด / สูงสุด / ค่ากลาง
- **จำนวนรอบที่ไม่ยิงเลย** ← สำคัญที่สุด ห้ามตัดทิ้ง
- เงื่อนไขแวดล้อมที่สังเกตได้ (จอเปิด/ปิด, จำนวนอุปกรณ์ BLE รอบตัว)

### การทดลองแยกที่ควรทำคู่กัน

ในโหมด foreground ให้ **หยุด ranging/scan ให้หมด** เหลือแค่ region monitoring
อย่างเดียว แล้วถอดแบต

- ถ้า exit ยิงสม่ำเสมอขึ้น → ranging เป็นตัวรบกวน
- ถ้ายังแกว่งเหมือนเดิม → เป็นพฤติกรรมของ CoreLocation เอง

ทั้งสองข้อสรุปนี้เปลี่ยนคำแนะนำที่จะให้ทีมแอป จึงคุ้มที่จะแยกออกจากกัน

## 9. เคสข้อ 16 — region flapping ระยะยาว (วางนิ่งข้ามคืน)

**เคสนี้วัดคนละเรื่องกับเคสอื่นทั้งหมด:** เคสอื่นวัด "ตอบสนองเร็วแค่ไหนเมื่อมีอะไร
เกิดขึ้น" เคสนี้วัด **"เงียบพอหรือเปล่าเมื่อไม่มีอะไรเกิดขึ้น"** — ระบบที่ตอบสนอง
เร็วแต่ยิง event มั่วตอนไม่มีอะไรเกิดขึ้น ใช้งานจริงไม่ได้ และปัญหาแบบนี้จะไม่โผล่
ในการทดสอบสั้น ๆ เลย ต้องปล่อยยาวเท่านั้นถึงจะเห็น

**ทำซ้ำเคสนี้ทุกครั้งที่ย้ายไปทดสอบสถานที่ใหม่** — ผลขึ้นกับสภาพสัญญาณของที่นั้น
มากกว่าขึ้นกับโค้ด

### ขั้นตอน

1. ทำการเตรียมมาตรฐาน (§0) ให้ครบ
2. **บันทึกสภาพแวดล้อมก่อนเริ่ม — ห้ามข้าม เพราะย้อนกลับมาวัดทีหลังไม่ได้:**
   - ระยะทางระหว่างมือถือกับ beacon (เมตร)
   - มีอะไรกั้นระหว่างกลาง (ผนัง โลหะ ตัวคน ฯลฯ)
   - จำนวน beacon อื่นที่อยู่ในระยะ
   - มือถือวางบนอะไร (โต๊ะไม้ / โลหะ / ในกระเป๋า)
3. **วางทุกอย่างนิ่ง** — ห้ามขยับมือถือ ห้ามขยับ beacon ห้ามถอดแบต
4. ล็อกเครื่องให้จอดับ
5. **ทิ้งไว้อย่างน้อย 8 ชั่วโมง** (ข้ามคืนสะดวกที่สุด)
6. เช้ามาเปิดแอป → กด "ดู log" → ส่งไฟล์ log ออกมา

### วิเคราะห์ผล

อย่านับด้วยตา — ใช้สคริปต์ในรีโป:

```bash
dart run tool/analyze_region_log.dart <ไฟล์>.log
```

สคริปต์จะให้ครบทั้งจำนวน enter/exit, ระยะเวลาแต่ละช่วง, มัธยฐาน/p90,
histogram, ชั่วโมงที่ flap ถี่ที่สุด, ตรวจว่า enter/exit สลับกันครบคู่ และจำลอง
ผลของค่า debounce ต่าง ๆ

**⚠️ เวลารายงานจำนวน enter ต้องระบุด้วยว่านับแบบไหน** — สคริปต์คืนสามค่า
(นับดิบ / ตัด artifact ของการส่ง event ค้างออก / ช่วงที่มี exit ปิดครบคู่) ตัวเลข
จากคนละรอบเทียบกันได้ก็ต่อเมื่อใช้นิยามเดียวกัน

### สิ่งที่ต้องบันทึกลงไฟล์สถานะ

- จำนวน enter/exit ทั้งสามแบบ + ระยะเวลาที่ทิ้งไว้
- สภาพแวดล้อมทั้ง 4 ข้อจากขั้นตอนที่ 2
- สถานะเครื่อง (ล็อก/จอดับ/แอปอยู่เบื้องหลัง)
- **commit ไฟล์ log ดิบเข้า `docs/test-data/`** ตามกติกาใน README ของโฟลเดอร์นั้น
  (ตรวจข้อมูลส่วนบุคคลก่อน) — ไม่งั้นตัวเลขที่รายงานจะตรวจย้อนกลับไม่ได้

**เกณฑ์ว่าเท่าไหร่ถือว่ายอมรับได้ อยู่ในข้อ 16 ของไฟล์สถานะ** — ที่นั่นที่เดียว

## 10. เคสข้อ 18 — ปิด Bluetooth ระหว่างเฝ้า region แล้ว `didExitRegion` ยิงหรือไม่

**สิ่งที่กำลังพิสูจน์:** เมื่อผู้ใช้ปิด Bluetooth ขณะที่ `CLBeaconRegion` ถูกเฝ้าอยู่
CoreLocation **ยิง `didExitRegion` ออกมาหรือไม่**

**ทำไมเคสนี้ต้องทำก่อนเริ่มเขียน port ฝั่ง iOS:** ค้นเอกสารของ Apple แล้วไม่พบประโยค
ที่ระบุพฤติกรรมนี้ (บันทึกไว้ที่ `docs/sources/ios_sensing_availability.md` หัวข้อ
"หาแหล่งอ้างอิงไม่ได้") · ผลของเคสนี้เปลี่ยนการออกแบบชั้นกรอง visit โดยตรง:

| ถ้าผลออกมาว่า | แปลว่า |
|---|---|
| **ยิง `didExitRegion`** | ฝั่ง iOS จะเจอบั๊ก visit ปลอมแบบเดียวกับ Android **และ `SensingLost` ช่วยไม่ได้ถ้า `exit` มาถึงก่อนที่เราจะรู้ตัวว่าตาบอด** — ลำดับการป้อน observation ต้องออกแบบใหม่ |
| **ไม่ยิงอะไรเลย** | การปิด Bluetooth มองไม่เห็นจากฝั่ง region monitoring · `SensingLost` ที่ป้อนจาก `centralManagerDidUpdateState` ครอบได้ตามที่ออกแบบไว้ |

### ⚠️ กับดักของเคสนี้ — อ่านก่อนลงมือ

**บรรทัด `exit` หนึ่งบรรทัดหลังปิด Bluetooth ยังไม่ใช่คำตอบ** — เคสข้อ 16 วัดได้ว่า
region flapping เกิดขึ้นเองตลอดคืนโดยไม่มีใครแตะอะไรเลย บรรทัด `exit` ที่โผล่มาหลัง
ปิด Bluetooth จึงอาจเป็น flap ปกติที่บังเอิญตรงจังหวะ

**ตัวแยกที่ใช้ได้จริงคือรูปแบบ ไม่ใช่บรรทัดเดียว:**

- flap ปกติ = `enter`/`exit` **สลับกันไปมา**
- ตาบอดจริง = `exit` แล้ว **เงียบสนิท ไม่มี `enter` ตามมาเลย** ตลอดช่วงที่ Bluetooth ปิด

จึงต้อง**เก็บช่วง baseline ก่อนปิด Bluetooth ในคืนเดียวกัน**เพื่อเทียบอัตรา flap —
ห้ามเทียบกับตัวเลขจากคืนอื่นหรือเครื่องอื่น

### ขั้นตอน

1. ทำขั้นเตรียมทั้งหมดใน §0 · **จดรุ่น iPhone และเวอร์ชัน iOS ลงตารางก่อนเริ่ม**
   (`Settings → General → About`) — ห้ามเริ่มถ้ายังไม่ได้จด
2. วาง K9P นิ่ง ๆ ข้างเครื่อง **ไม่ถอดแบตตลอดทั้งเคส** และไม่ขยับทั้งคู่
3. เริ่มเฝ้า region · ยืนยันว่าได้ `enter` แล้วกด home ให้แอปอยู่เบื้องหลัง
4. **เก็บ baseline 60 นาที** โดยไม่แตะเครื่องเลย — ช่วงนี้คืออัตรา flap ปกติของคืนนี้
   ที่จะใช้เป็นตัวเทียบ
5. **ปิด Bluetooth จาก Settings** (ไม่ใช่ Control Center) · **จดเวลาให้ละเอียดถึง
   วินาที**
6. **ไม่แตะเครื่องเลย 60 นาที** และ **ห้ามเปิดแอป** ตลอดช่วงนี้ — การเปิดแอปเขียน
   บรรทัด `launch` และอาจทำให้ลงทะเบียนใหม่ ซึ่งทำลายเคสทั้งเคส
7. ดึง log ออกมาตรวจ **โดยไม่เปิดแอป** (คำสั่งใน §0.1)
8. เปิด Bluetooth กลับ · จดเวลา · รออีก 30 นาทีโดยไม่แตะเครื่อง แล้วดึง log อีกครั้ง
9. ทำซ้ำอย่างน้อย 3 รอบ — **บันทึกรอบที่ไม่มี event ด้วย** ตามกติกาหัวไฟล์

### เคสย่อย 18b — ปิดจาก Control Center

## 11. ยืนยัน ADR-16 บนอุปกรณ์จริง — `hasEverBecomeActive` ภายใต้ UIScene lifecycle

**ทำไมต้องมีหัวข้อนี้แยก:** ARCHITECTURE.md ADR-16 แก้บั๊กที่ `hasEverBecomeActive`
ค้าง `false` ตลอดชีพ process ทุกกรณี (แอปนี้ประกาศ `UIApplicationSceneManifest`)
ด้วยการเพิ่ม `NotificationCenter` observer ของ
`UIApplication.didBecomeActiveNotification` — โค้ด**คอมไพล์ผ่านและมี XCTest
คลุมตรรกะการตัดสิน (`AppDelegate.runContext`) แล้ว** แต่นั่นพิสูจน์ได้แค่ว่า
ฟังก์ชันคืนค่าตามสัญญาที่ตั้งใจ **ไม่ได้พิสูจน์ว่า iOS post
`didBecomeActiveNotification` จริงในสภาพแวดล้อมของแอปนี้** ซึ่งเป็นสมมติฐานที่มา
จากเอกสาร Apple ล้วน ๆ (ยังไม่เคยรันจริงบนอุปกรณ์) — ดู ADR-16 หัวข้อ 5 สำหรับ
รายการที่ยังพิสูจน์ไม่ได้ครบ

**เกี่ยวกับข้อ 12 ในไฟล์สถานะโดยตรง:** สถานะของข้อ 12 บันทึกไว้แล้วจากการ
ทดสอบ 30 ส.ค. 2026 (ดูรายละเอียดที่ไฟล์สถานะ) แต่เหตุผลรองรับเดิมอ้าง
`everActive=false` ซึ่ง ADR-16 หัวข้อ
0 และ 4 อธิบายว่า**ไม่มีน้ำหนักพิสูจน์อะไรเลย** (ค่านั้นเป็น `false` เสมอไม่ว่า
ความจริงจะเป็นอะไรเนื่องจากบั๊กเดิม) — สามข้อด้านล่างคือสิ่งที่ต้องทำซ้ำเพื่อให้
ข้อ 12 มีเหตุผลรองรับที่เชื่อได้จริงหลังแก้โค้ดแล้ว ไม่ใช่แค่ "คอมไพล์ผ่าน"

### 11a. observer ยิงจริงตอนแอปขึ้น active ปกติ

**สิ่งที่กำลังพิสูจน์:** `UIApplication.didBecomeActiveNotification` ถูก post
จริงภายใต้ `UIApplicationSceneManifest` บนอุปกรณ์จริง (ไม่ใช่แค่บน simulator —
XCTest ที่มีอยู่ (`testDidBecomeActiveObserverFiresOnRealAppLifecycle`) รันเป็น
hosted test bundle ข้างในแอปจริง แต่ยังไม่เคยรันบน**อุปกรณ์จริง** และมีเงื่อนไข
ว่าแอปต้องอยู่ `state=active` ตอนเทสต์รันถึงจะพิสูจน์อะไรได้ — ต้องยืนยันด้วยตา
ประกอบด้วย)

1. ทำการเตรียมมาตรฐาน (§0) ให้ครบ
2. เปิดแอปตามปกติ (แตะไอคอน) จนขึ้นหน้าจอหลัก
3. เปิดหน้า "ดู log" แล้วกดปุ่ม self-test เครื่องมือบันทึกหลักฐาน (ปุ่มที่เขียน
   1 บรรทัดแล้วอ่านกลับทันที)
4. **อ่านบรรทัดสัญญาณดิบที่เขียนได้ — ต้องเห็น `everActive=true` พร้อม
   `state=active`**

### เกณฑ์อ่านผล (11a)

| ที่เห็น | แปลว่า |
|---|---|
| `everActive=true state=active` | observer ทำงานจริงตามที่ ADR-16 ออกแบบไว้ |
| `everActive=false state=active` | **รูปแบบเดียวกับหลักฐานบั๊กเดิมที่ ADR-16 หัวข้อ 0 บันทึกไว้** (process `ed11d170`, บรรทัด `exit` 13:57:11) — แปลว่าบั๊กยังไม่ถูกแก้จริง หรือ observer ไม่ทำงานบนอุปกรณ์จริงทั้งที่ทำงานบน simulator ให้รายงานกลับ `flutter-dev` พร้อมบรรทัด log นี้ทันที |

### 11b. process ที่ถูกปลุกเบื้องหลัง ไม่เคย active เลย ยังให้ `false` ถูกต้อง

**สิ่งที่กำลังพิสูจน์:** เคส "ไม่มี scene ถูก connect เลย" ตามที่ ADR-16 หัวข้อ
1.4 ออกแบบไว้ (แถวที่ 3 ของตารางข้อกังวล) — process ที่ถูกปลุกเบื้องหลังล้วน ๆ
ไม่มี UI เกิดขึ้นเลย ต้องไม่มีทางได้ `everActive=true` ปลอม ๆ

1. ทำเหมือนขั้นตอนข้อ 12 เดิม (ดู §8): ลบแอปติดตั้งใหม่ → ตั้งค่ามาตรฐาน (§0) →
   **ปัดแอปทิ้งจาก app switcher** → ถอด/ใส่แบต K9P → รอ
2. **ห้ามเปิดแอปเลยตลอดขั้นตอนนี้** — เปิดแอปจะทำให้ scene connect และแอป active
   ทันที ซึ่งทำลายเคสที่ตั้งใจทดสอบ
3. ดึง log ออกมาตรวจโดยไม่เปิดแอป (วิธีดูใน §0.1)

### เกณฑ์อ่านผล (11b)

| ที่เห็น | แปลว่า |
|---|---|
| บรรทัด `enter`/`exit` มี `everActive=false state=background` | ถูกต้องตามที่ ADR-16 หัวข้อ 1.4 ออกแบบไว้ — เหมือนผลเดิมของข้อ 12 ทุกประการ (ค่านี้ตรงกันทั้งก่อนและหลังแก้บั๊ก เพราะเป็นเคสที่ไม่เคย active จริง) |
| บรรทัด `enter`/`exit` มี `everActive=true` ทั้งที่ไม่มีใครเปิดแอปเลย | **ผิดปกติ — ห้ามสรุปเอง** ให้ตรวจว่ามีเส้นทางอื่นเรียก `applicationDidBecomeActive`/`didBecomeActiveNotification` โดยไม่ได้ตั้งใจหรือไม่ แล้วรายงานกลับ `flutter-dev` |

⚠️ **เคสนี้เพียงลำพังแยกไม่ออกว่า "หลังแก้บั๊ก" กับ "ก่อนแก้บั๊ก" ต่างกันตรงไหน**
เพราะทั้งสองแบบให้ `false` เหมือนกัน (ก่อนแก้: ค้าง `false` เสมอโดยบั๊ก / หลังแก้:
`false` เพราะไม่เคย active จริง) — **11c ด้านล่างต่างหากที่เป็นตัวพิสูจน์จริงว่า
บั๊กถูกแก้แล้ว** เพราะมันบังคับให้ process ต้อง active แล้วดูว่าบรรทัดหลังจากนั้น
เปลี่ยนจาก `relaunchedFromTerminated` เป็น `background` หรือไม่

### 11c. process อายุยืนที่ active กลางทาง ต้องแยก `background` จาก `relaunchedFromTerminated` ได้จริง

**สิ่งที่กำลังพิสูจน์:** จำลองรูปแบบของ process `ed11d170` (ADR-16 หัวข้อ 3) —
ถูกปลุกเบื้องหลัง แล้ว**ภายหลัง**ผู้ใช้เปิดแอปขึ้นมาดูจริง (แอป active) แล้วกลับไป
เบื้องหลังอีกครั้งโดยไม่ถูกฆ่า **นี่คือเทสต์เดียวที่แยกความแตกต่างระหว่างพฤติกรรม
ก่อนแก้กับหลังแก้ได้จริง** — ก่อนแก้บั๊ก บรรทัดหลัง active จะยังผิดเป็น
`relaunchedFromTerminated` เสมอ (ตามที่ ADR-16 หัวข้อ 0 พิสูจน์จากอุปกรณ์จริงแล้ว)
ส่วนหลังแก้ต้องกลายเป็น `background`

1. ทำการเตรียมมาตรฐาน (§0) ให้ครบ · ล้าง log
2. **ปัดแอปทิ้งจาก app switcher** ให้ process ตายจริง
3. ถอด/ใส่แบต K9P → จดเวลา → รอจนเห็นบรรทัด `launch` ตามด้วย `enter`/`exit` ที่
   เป็น `relaunchedFromTerminated` (เหมือนขั้นตอนข้อ 12 เดิม) — **ห้ามเปิดแอป
   ในขั้นตอนนี้**
4. **จากนั้นเปิดแอปขึ้นมาดูจริง** (แตะไอคอน) ปล่อยให้ขึ้นหน้าจอหลักอย่างน้อยไม่กี่
   วินาที เพื่อให้แน่ใจว่า process ขึ้นถึง `state=active` แล้วจริง — ตรวจได้จากปุ่ม
   self-test (ดูข้อ 11a)
5. **กด home ให้แอปไปเบื้องหลัง — ห้ามปัดทิ้ง** (process ต้องยังมีชีวิตอยู่)
6. ถอด/ใส่แบต K9P อีกครั้ง → จดเวลา → รอ
7. เปิดแอปดู log เทียบบรรทัดของ `enter`/`exit` รอบแรก (ก่อน active) กับรอบที่สอง
   (หลัง active)

### เกณฑ์อ่านผล (11c)

| ที่เห็น | แปลว่า |
|---|---|
| รอบแรก `relaunchedFromTerminated` **และ** รอบสอง (หลัง active) เป็น `background` | บั๊กถูกแก้จริง — แยกสองสถานะได้ถูกต้องตามที่ ADR-16 ออกแบบไว้ |
| ทั้งสองรอบเป็น `relaunchedFromTerminated` เหมือนกัน ทั้งที่ระหว่างนั้นเปิดแอปขึ้นมา active จริง | **บั๊กยังไม่ถูกแก้ หรือ observer ไม่ทำงานบนอุปกรณ์จริง** — รูปแบบเดียวกับ `ed11d170` ที่ ADR-16 หัวข้อ 3 บันทึกไว้ก่อนแก้ ให้รายงานกลับ `flutter-dev` พร้อมทั้งสองบรรทัด log |
| รอบสองเป็น `foreground` แทนที่จะเป็น `background` | แอปยังไม่ทันกลับไปเบื้องหลังตอนถอดแบต ให้ตรวจว่ากด home สำเร็จก่อนถอดแบตจริง แล้วทำซ้ำ |

**บันทึกทั้งสามผล (11a-11c) ลงหมายเหตุของข้อ 12 ในไฟล์สถานะ** — ไม่ใช่เพิ่มเลขข้อ
ใหม่ เพราะเป็นการยืนยันเหตุผลรองรับของข้อ 12 เดิม ไม่ใช่เคสใหม่

## ภาคผนวก — บทเรียนจากการทดสอบที่ผ่านมา

รวมไว้เพื่อไม่ให้เสียเวลาซ้ำกับเรื่องเดิม

### 1. เครื่องมือวัดต้องรอดในสภาพที่กำลังทดสอบ

โปรเจกต์นี้ชนแพตเทิร์นนี้มาแล้วหลายครั้ง และอาการเหมือนกันหมดคือ **"ระบบเงียบ"**
แล้วเราไปสรุปว่าฟีเจอร์ไม่ทำงาน ทั้งที่มันทำงานอยู่:

| ครั้งที่ | เครื่องมือวัดที่ตาย | ทำไมถึงตาย |
|---|---|---|
| 1 | notification ตอน foreground | iOS ไม่แสดง banner ถ้าไม่ implement `willPresent` delegate จึงดูเหมือนไม่มี event |
| 2 | log ที่เขียนผ่าน Dart | ต้องมี Flutter engine ซึ่งไม่มีตอน background cold launch — ตายพร้อมกับสิ่งที่ควรวัด |
| 3 | Xcode debugger / console | หลุดทันทีที่แอปถูก force quit ไม่มีทางเห็นอะไรผ่าน console |

**กฎที่ได้:** ก่อนสรุปว่าอะไรไม่ทำงาน ต้องพิสูจน์ก่อนว่า**เครื่องมือวัดยังมีชีวิตอยู่**
ในสภาพที่กำลังทดสอบ — บรรทัด `launch` ใน log มีไว้เพื่อการนี้โดยเฉพาะ

### 2. เวลารอไม่พอ = ผลลบลวง

exit ช้ากว่า enter มากอย่างเป็นระบบ (CoreLocation รอยืนยันก่อนประกาศ exit เพื่อกันการ
กระพริบจาก beacon ที่สัญญาณขาด ๆ หาย ๆ) ถ้ารอแค่ 10-20 วินาทีแล้วสรุปว่าไม่ทำงาน จะไล่
หาบั๊กที่ไม่มีอยู่จริง — **รออย่างน้อย 3-5 นาทีทุกครั้งก่อนสรุป**

### 3. beacon ตัวอื่นที่ใช้ UUID เดียวกันทำให้ exit ไม่ยิง

`didExitRegion` ยิงก็ต่อเมื่อ **ไม่เหลือ beacon ที่ตรงกับ constraint ของ region นั้น
ในระยะเลยแม้แต่ตัวเดียว** — ตามนิยามของ region ที่ประกอบจาก
`CLBeaconIdentityConstraint` ถ้ามี K9P ตัวอื่น (เช่นของเพื่อนร่วมงาน) ที่ยังใช้ UUID
โรงงานเดียวกันอยู่ในระยะ การถอดแบตตัวเดียวจะไม่ทำให้ออกจาก region

**ทดสอบในที่ที่มี beacon ตัวเดียวเสมอ** หรือใช้ region ที่เจาะจง major/minor
และนับ beacon รอบตัวก่อนเริ่มทุกครั้ง (§0 ข้อ 10)

> ข้อนี้เป็นการอนุมานจากนิยามของ region + `CLBeaconIdentityConstraint`
> **ยังไม่ได้ทดสอบยืนยันบนอุปกรณ์จริงในโปรเจกต์นี้** ถือเป็นข้อควรระวังตอนวางแผน
> ทดสอบ ไม่ใช่ข้อเท็จจริงที่วัดมาแล้ว

### 4. region ค้างจาก build เก่า

โค้ดรุ่นก่อน ADR-10 สะสม region ไว้ในระบบ (ตัว `stopMonitoring` วนจาก dictionary ใน
หน่วยความจำซึ่งว่างเปล่าเสมอใน process ใหม่ จึงไม่เคยลบของเก่าได้) ทำให้ผลปนกันและ
ตัวนับเพดาน 20 region นับของค้างด้วย

**ลบแอปติดตั้งใหม่ก่อนทดสอบทุกครั้ง** (§0 ข้อ 1)

### 5. ไฟล์ Swift ใหม่ต้องเพิ่มเข้า `project.pbxproj`

ถ้าไม่เพิ่ม ไฟล์จะไม่ถูกคอมไพล์**โดยไม่มี error ใด ๆ** — build เขียวแต่โค้ดไม่เคยรัน
ซึ่งเป็น failure mode ที่อันตรายที่สุดเพราะทุกอย่างดูปกติ

ยืนยันด้วย `nm` ว่าเจอ symbol จริง และเช็คว่าไฟล์ `.o` อยู่ใน `Runner.LinkFileList`

### 7. timestamp ใน log คือ "เวลาที่แอปได้รับ event" ไม่ใช่ "เวลาที่ข้ามขอบเขต"

ตอน process ถูกปลุกขึ้นมาใหม่ ระบบจะส่ง event ที่คิวไว้มาติด ๆ กัน — พบคู่ exit→enter
